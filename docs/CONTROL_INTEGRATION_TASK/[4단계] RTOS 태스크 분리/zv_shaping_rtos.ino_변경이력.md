## 절대 규칙

> **제어 수식, 명령어, 출력 내용을 바꾸지 않는다. 실행 구조만 바꾼다.**

계산식은 복사만 했다. 손으로 다시 쓰지 않았다.

검증은 두 가지로 했다.

**① 문자열 전수 대조** — 두 파일의 리터럴을 모두 뽑아 비교했다.

```
3단계 131종 137개  /  4단계 137종 143개
사라진 출력 : 0건
새 문자열   : "%s\n"(qprintln 내부)  "ctrl"  "io"  그리고 [rtos] 계측 줄 2개
```

**② 삭제된 코드 줄 전수 확인** — 들여쓰기·주석을 무시하고 원본에서 없어진 줄을
전부 뽑았더니 아래 6가지뿐이었고, **제어 수식 줄은 하나도 없었다.**

| 없어진 줄 | 수 | 왜 |
|---|---|---|
| `float GAIN = ...` 등 선언 | 17 | `volatile` 이 붙음 |
| `Serial.printf` / `println` | 13 | `qprintf` / `qprintln` 로 (내용 동일) |
| `arm` `stop` `t` `z` 처리 | 7 | 요청 큐로 |
| `float &d = ...` | 1 | `volatile float &d` |
| `zvRecalc(); zvClear();` | 4 | 잠금 추가 |
| `loop()` 머리 + 스트림 printf | 15 | `vTaskDelayUntil` + 스냅샷 큐 |

## 무엇이 바뀌었나

```
3단계                          4단계
loop() {                       ctrl (코어1, 우선순위6)   io (코어0, 우선순위2)
  handleSerial()                 vTaskDelayUntil(10ms)     큐에서 꺼내 출력
  10ms 지났나?                   요청 실행 (arm/stop/t/z)   handleLine()
  IMU→필터→ZV→제어→CAN           IMU→필터→ZV→제어→CAN
  로그 출력                      숫자만 큐에 ──────────────→
}                              loop() = vTaskDelay(1000)  껍데기
```

`ctrl` 본문의 순서는 3단계 `loop()` 와 같다.
`readIMU` → 상보필터 → 이상감지 → `drainCAN` → 합력벡터 → ZV → 제어 →
`sendBoth` → 출력 → 2초 상태.

`loop()` 를 지우지 않은 이유는 아두이노 `loopTask` 가 태스크 워치독에게 살아있다고
보고하는 역할을 겸하기 때문이다. 지우면 리셋이 걸릴 수 있어 껍데기로 남겼다.

### `dt` 가 가정에서 약속으로

`const float dt = 0.01;` 을 상보필터와 슬루(`MAX_RATE * dt`)가 쓴다.
3단계에는 그것을 보장하는 장치가 없었다 — 안 늦었을 뿐이다.
`vTaskDelayUntil` 은 OS 가 지킨다.

## 태스크를 나눠서 새로 생긴 위험 6가지

### ① 두 태스크가 동시에 Serial 에 쓰면 줄이 섞인다

한 줄 안에서 `pre_pitch` 와 `cmd_pitch` 를 짝지어 읽는 분석이 무너진다.

**`Serial` 은 `io` 태스크만 만진다.** `ctrl` 은 큐에 넣고 지나간다.

```cpp
QueueHandle_t qEvt  = NULL;     // 텍스트 12통  — 모터이상·폭주차단·두절·DISARM 이유
QueueHandle_t qSnap = NULL;     // 샘플 32통   — 33Hz 스트림
```

**큐를 두 개로 나눈 이유**가 있다. 하나로 두면 PC 가 멈춘 순간 샘플이 자리를
먼저 차지해서 **정작 원인이 되는 이벤트가 버려진다.** 제어는 돌아도 사후 분석이
막힌다. `io` 는 `qEvt` 를 먼저 비운다.

스트림은 **숫자만** 큐에 넣는다. `%.2f` 13개 포맷(수백 µs)은 `io` 가 진다.

`ctrl` 쪽 출력은 **대기 0** 이다. PC 가 안 읽어서 큐가 차면 로그 한 줄마다 제어가
멈추는데, 그걸 없애려고 나눈 것이라 앞뒤가 안 맞는다. 잃은 줄은 `dgEvtDrop` 으로 센다.

### ② `arm` 은 250ms, `t` 는 8초 블록한다

`io` 에서 돌리면 그동안 `ctrl` 이 CAN 지령을 계속 쏜다. **영점 잡는 중에 지령이
끼어드는 셈이라 3단계에서는 물리적으로 불가능한 상황이 된다.**
`motorsArm()` 은 I2C 도 쓰는데 `Wire` 는 두 태스크가 동시에 만지면 깨진다.

**요청 큐로 넘기고 `ctrl` 이 직접 실행한다.** 같은 코드가 같은 것을 멈춘 채로 돈다.

```cpp
QueueHandle_t qCmd = NULL;        // 명령 6통
volatile bool ctrlBusy = false;   // arm / t 실행 중
```

- **변수 하나가 아니라 큐**여야 한다. 변수면 `ctrl` 이 읽고 지우는 사이에 들어온
  명령이 사라지고, 연속 입력은 앞의 것을 덮어쓴다.
- `stop` 은 자리가 없으면 앞 명령을 하나 버려서라도 넣는다.
- `ctrlBusy` 중에는 `Serial.read()` 를 하지 않는다. 바이트가 UART 버퍼에 그대로
  쌓였다가 끝난 뒤 처리되므로 **3단계와 동작이 같다.** (3단계는 sweep 8초 동안
  `handleSerial()` 이 아예 안 불린다. 만약 `io` 가 계속 파싱하면 sweep 도중
  `dr` 이 들어와 복귀 직후 roll 방향이 뒤집힐 수 있다.)
- `ctrlBusy` 는 **`arm` 과 `t` 가 끝날 때만** 푼다. 공통으로 풀면 큐에
  `[z, arm]` 이 있을 때 `z` 가 먼저 풀어버려 arm 250ms 동안 파서가 다시 열린다.
- 큐에 못 넣었으면 `ctrlBusy` 를 되돌린다. 안 그러면 풀어줄 사람이 없어 파서가
  영영 멈춘다.

### ③ ZV 계수는 네 개가 한 세트다

`zvRecalc()` 가 `zv_n1` `zv_A1` `zv_A2` `zv_A3` 를 묶어서 바꾸고,
`zvClear()` 는 링버퍼 float 256개를 지운다. 중간에 읽으면 섞인 조합이 나온다.

```cpp
portMUX_TYPE zvMux = portMUX_INITIALIZER_UNLOCKED;
```

`zvRecalc` · `zvClear` · `ctrl` 의 ZV 계산 블록 세 곳을 잠근다.
`zv1` `zf` `zd` `zm` 각각의 **변경 전체가 하나의 임계구역**이다.
`ZV_ON = ...` 만 락 밖에 두면 그 사이 한 틱이 지나간다.

요청 큐 대신 락을 쓴 이유는 `zd` 가 계산 직후 `A1/A2/A3` 를 바로 찍기 때문이다.
미루면 옛 값이 찍혀 출력이 달라진다.

문자열 변환(`s.substring(2).toInt()`)은 **락 밖에서** 먼저 끝낸다. 임계구역 안에서
`String` 을 만들면 인터럽트가 막힌 채로 힙을 건드린다.

홑겹 변수(`GAIN` `MOTOR_KP` `MAX_RATE` `ZV_ON` `stream` …)는 32비트 단일 접근이
원자적이라 `volatile` 만 붙였다. 옛 값 아니면 새 값이지 섞인 값은 안 나온다.

### ④ `readStringUntil` 은 최대 1초 막힌다

터미널이 글자를 나눠 보내기만 해도 그동안 큐를 못 비운다. 32칸 샘플 큐는
33Hz 에서 1초면 찬다. **문자 단위 비동기 파서**로 바꿨다. 명령·응답 내용은 같다.

### ⑤ 재동기는 특정 명령 뒤가 아니라 매 틱

`configSensor()` 는 정상 실행만으로 150ms 를 쓰고(`delay(50)` + `delay(100)`),
I2C 가 응답 없으면 최대 50ms 를 더 멈춘다. `arm` 뒤에만 시계를 맞추면 이런 경우를
놓쳐서 `vTaskDelayUntil` 이 밀린 틱을 10ms 간격 없이 연속으로 따라잡는다.

```cpp
if ((TickType_t)(xTaskGetTickCount() - xLastWake) >= pdMS_TO_TICKS(20)) {
  xLastWake = xTaskGetTickCount();
  dgResync = dgResync + 1;
}
```

### ⑥ 바쁜 대기를 만들면 워치독이 보드를 리셋한다

`ctrl` 은 `vTaskDelayUntil`, `io` 는 `xQueueReceive(…, 5ms)` 로 양보한다.
`while (!Serial.available()) {}` 같은 것을 쓰면 IDLE 태스크가 굶는다.

## 실측값을 기본값으로

3단계 기본값은 매번 손으로 넣어야 해서 빠뜨리는 사고를 두 번 겪었다.
시리얼 명령으로 여전히 바꿀 수 있다.

| 항목 | 3단계 | 4단계 | 근거 |
|---|---|---|---|
| `MAX_RATE` | 30 | **120** | 요구 변화율 p95 가 101~112 °/s. 30 이면 지령의 31% 가 잘려 ZV 성형이 무너진다 |
| `MOTOR_KP` | 1.0 | **2.0** | 드룹 54~82% → 89% |
| `MOTOR_KD` | 0.13 | **0.13** | `Kd ∝ √(Kp+k)`, `k ≈ 0.28 N·m/rad` |

`k` 는 트레이 무게중심이 축보다 아래에 있어 생기는 복원 강성이다.
정지 구간에서 `act/cmd` 가 일정 비율로 모자란 것(오프셋 −0.38°/+0.10°, 거의 0)에서
`k = Kp·(1/droop − 1)` 로 냈다. 마찰이면 비율이 아니라 고정 오프셋으로 나타난다.

### ZV 성형은 슬루를 더 걸지 않는다

같은 로그에서 ZV 만 뺀 반사실 계산을 돌렸다 (`ref_*` 와 `zv_*` 가 둘 다 기록돼 있다).

| | ZV 끔 | ZV 켬 |
|---|---|---|
| pitch 슬루 걸림 | 10.8% | 10.9% |
| roll 슬루 걸림 | 12.3% | **10.0%** |
| roll 요구 p95 | 133 °/s | **122 °/s** |

임펄스 합이 1이고 둘 다 양수라 **가중 이동평균**이다. 계단이 하나 늘지만 각 계단
높이가 절반이라 최대 변화율은 오히려 내려간다.
(절대값은 33Hz 로그를 100Hz 로 재구성한 탓에 부풀려져 있다. 차이만 유효하다.)

## 슬루 판정용 필드

출력 앞에 세 개를 붙였다.

```
t:23561,pre_pitch:-2.62,pre_roll:-8.91,pitch:2.36,ref_pitch:0.82,zv_pitch:0.82,...
```

| 필드 | 왜 |
|---|---|
| `t` | 펌웨어 시각. PC 수신 시각에는 USB 지터가 섞여 변화율 계산에 못 쓴다 |
| `pre_*` | 슬루 **걸기 전** 지령(`lpf_*`). `cmd` 와 다르면 잘린 것이고, 차이가 잘려나간 양이다 |

`cmd` 만 보면 잘린 흔적이 이미 지워져 알 수가 없다. `MAX_RATE = 120` 을 고른
근거가 이 `pre_*` 에서 나왔다.

기존 `ref_*` · `zv_*` 는 그대로다. 새 변수를 만든 게 아니라 이미 있는 `lpf_*` 를
출력에 실었을 뿐이라 제어 계산은 한 줄도 안 바뀌었다.

주기는 조건이 `> 20` 이라 10ms 루프에서 **30ms** 마다 나간다. 33Hz 다 (주석의 50Hz 수정).

## CAN 송신 대기 0

```cpp
if (twai_transmit(&m, 0) != ESP_OK) dgTxFail = dgTxFail + 1;   // sendMIT
```

`sendMIT` 은 50Hz 로 계속 나가는 주기 지령이라 한 장 버려도 20ms 뒤 다음 장이 간다.
반면 5ms 를 기다리면 두 축이 10ms — **한 틱 예산 전부**다.

**실측 근거.** 모터 전원을 끈 채 `arm` 하면 CAN ACK 가 없어 송신 큐가 막힌다.

| | 5ms 대기 | 대기 0 |
|---|---|---|
| `10ms초과` | **17** | **1** |
| `TX실패` | 36 | 36 |

실패 **횟수**는 같고 **대기 시간**만 사라진다 (송신 큐 5칸이 차면 그 뒤는 어차피 실패).
정상 CAN 에서는 큐가 안 차므로 `TX실패 0` 이고 동작이 같다.

남은 1건은 `motorsDisarm` 의 `broadcastUniversal(0xFD)` 다. `sendUniversal` 은
비주기 명령이라 **한 장이 중요해서 5ms 를 그대로 뒀다.** 2축 × 5ms + 1ms = 11.0ms 이고
실측 11,023 µs 와 맞는다. CAN 이 이미 죽었을 때 정지하는 순간 한 번이라 그대로 둔다.

## 실기 검산

`RTOS_DIAG` 계측을 넣고 실기에서 확인했다.
`t:` 간격만으로는 100Hz 누락을 못 잡는다 — 출력 게이트가 틱 안에 있어서
**틱 하나가 빠져도 앞뒤 출력이 30ms 로 보인다.** 그래서 틱 자체를 쟀다.

### 모터 전원 OFF, arm 안 함

```
최대틱 490~630us   10ms초과 0   재동기 0   TX실패 0   드롭 전부 0
```

### 모터 전원 ON, `arm`, 26초 캡처

```
최대틱 550~593us   10ms초과 0   재동기 1   TX실패 0   드롭 전부 0
피드백 2523회 (100/s = 50Hz × 2축)
```

`재동기 1` 은 `arm` 의 `delay` 250ms 때 한 번이다. 설계대로다.
계측 시작점을 명령 처리 **뒤**로 두었다. `arm` 의 의도된 정지를 같이 세면
(실측 270ms 로 찍혔다) 제어 틱이 늦었는지를 볼 수 없다.

### 3단계 로그와 비교

같은 도구(`capture.py` → `check_tuning.py`)로 같은 조건에서 비교했다.

| | 3단계 | 4단계 |
|---|---|---|
| pitch 드룹 | 89% | **89%** |
| pitch 추종오차 RMS | 3.31° | 3.18° |
| pitch 슬루 걸림 | 6% | 4% |
| roll 슬루 걸림 | 7% | 6% |
| pitch 요구 p95 | 101 °/s | 96 °/s |

**드룹이 정확히 같다.** 나머지 차이는 흔든 세기 차이다 (요구 변화율이 전반적으로
낮다 = 덜 세게 흔들었다). roll 드룹과 떨림은 계속 흔들어 정지 구간이 없어서
안 나왔다 — 다음에는 흔들다가 2초쯤 멈추기를 서너 번 섞어야 한다.

### 피드백 두절 워치독

모터 전원 없이 `arm` 했을 때 **302ms 만에 스스로 내려갔다.**

```
>>> ARMED  GAIN=1.00  ACC_GAIN=1.00  Kp=2.0  Kd=0.13  제한 ±25°
!! 피드백 302ms 끊김
>>> DISARM — 피드백 두절
```
