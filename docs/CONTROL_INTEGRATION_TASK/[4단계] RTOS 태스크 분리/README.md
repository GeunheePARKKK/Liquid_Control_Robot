# 4단계 — RTOS 태스크 분리

3단계 [`ZV_입력성형.ino`](../%5B3%EB%8B%A8%EA%B3%84%5D%20ZV%20%EC%9E%85%EB%A0%A5%EC%84%B1%ED%98%95/ZV_%EC%9E%85%EB%A0%A5%EC%84%B1%ED%98%95.ino) 에서 출발한다. 아직 코드 없음.

## 먼저 알아둘 것 — 이미 FreeRTOS 위에서 돌고 있다

ESP32 아두이노 코어는 FreeRTOS 위에 얹혀 있다. `setup()` / `loop()` 는
`loopTask` 라는 태스크 하나로 **코어 1 에 고정**되어 돌아간다.

그래서 4단계는 "RTOS 를 도입" 하는 것이 아니라 **한 덩어리 `loop()` 를
태스크로 쪼개는** 작업이다.

## 왜 쪼개야 하나 — 실측된 이유

### 시리얼이 대역폭의 61% 를 쓴다

| 항목 | 값 |
|---|---|
| 스트림 한 줄 | 140자 |
| 115200 8N1 전송 시간 | **12.3 ms/줄** |
| 출력 주기 | 20 ms (50Hz) |
| **점유율** | **61 %** |

제어 루프는 **10 ms** 주기다. 한 줄 보내는 데 12.3 ms 가 걸리므로 TX 버퍼
(기본 256바이트, 두 줄이 안 들어간다) 가 차면 `Serial.printf` 가 **블록**한다.
그 순간 제어 루프가 통째로 밀린다.

지금은 같은 태스크 안에 있어서 이것을 분리할 방법이 없다.

### 그 밖의 이유

| 현재 | 문제 |
|---|---|
| `drainCAN()` 을 루프에서 폴링 | 피드백이 늦게 반영된다 |
| `readStringUntil('\n')` 명령 파싱 | 최대 1초 블록 가능 (`Serial.setTimeout` 기본) |
| `lastLoop += 10000` 누산 | 밀리면 몰아서 실행. 재동기 코드로 막아뒀지만 근본 해결은 아니다 |

지금까지 잰 지연 150~180 ms 중 얼마가 여기서 오는지 아직 분리되지 않았다.

## 태스크 나누기 제안

| 태스크 | 주기 | 우선순위 | 코어 | 하는 일 |
|---|---|---|---|---|
| `ctrl` | 10 ms | 높음 | 1 | IMU 읽기 → 자세 → θ_ref → ZV → 지령 |
| `can_tx` | 20 ms | 높음 | 1 | MIT 프레임 송신 |
| `can_rx` | 블록 | 중간 | 0 | `twai_receive` 대기 → 피드백·이상 감지 |
| `io` | 20 ms | **낮음** | 0 | 스트림 출력, 명령 파싱 |
| `safety` | 100 ms | 높음 | 0 | 피드백 두절·위치 한계·IMU 이상 |

핵심은 **`io` 를 코어 0 의 낮은 우선순위로 빼는 것**이다. 시리얼이 아무리
막혀도 제어 루프가 안 밀린다.

`ctrl` 은 `vTaskDelayUntil` 로 주기를 잡는다. 지금의 누산 방식보다 지터가
작고 밀림 처리가 명확하다.

## 조심할 것 — 공유 변수

파라미터를 `io` 태스크가 쓰고 `ctrl` 태스크가 읽는다. 32비트 `float` 하나는
찢어지지 않지만 **여러 변수가 함께 맞아야 하는 곳**이 문제다.

### ZV 계수가 대표적이다

```cpp
void zvRecalc() {
  zv_n1 = ...;      // 반주기
  zv_A1 = ...;      // 진폭
  zv_A2 = ...;
  zv_A3 = ...;
}
```

`io` 가 `zv_n1` 을 새로 쓴 직후 `ctrl` 이 끼어들면, **새 지연에 옛 진폭**을
곱한 셰이퍼가 한 틱 동안 돌아간다. 지금은 한 태스크라 생길 수 없는 일이다.

계수 묶음을 구조체로 만들어 통째로 교체하거나(더블 버퍼), 뮤텍스로 감싼다.

### 그 밖

| 자원 | 접근 | 대책 |
|---|---|---|
| `zv_p[]` `zv_r[]` 링버퍼 | `ctrl` 만 | 단일 소유. 그대로 두면 된다 |
| `act_deg[]` `last_status[]` | `can_rx` 쓰기 / `ctrl`·`io` 읽기 | 원자적 읽기로 충분 |
| `armed` | 여러 태스크가 내릴 수 있다 | 플래그보다 이벤트그룹·큐가 안전 |
| I2C (`Wire`) | `ctrl` 만 | 다른 태스크에서 건드리지 말 것 |
| TWAI 드라이버 | 송수신 분리 | 드라이버가 스레드 안전. 큐 깊이는 확인 |

`motorsDisarm()` 을 여러 태스크에서 부를 수 있게 되면 경쟁이 생긴다. 안전
정지는 **큐나 이벤트그룹으로 한 곳에 모아** 처리하는 편이 낫다.

## 확인 방법

쪼개고 나서 좋아졌는지 숫자로 봐야 한다.

| 지표 | 어떻게 | 지금 값 |
|---|---|---|
| 제어 주기 지터 | `ctrl` 안에서 실제 간격 히스토그램 | 미측정 |
| 지령→실제 지연 | `capture.py` 상호상관 | 150~180 ms |
| 슬루 포화 비율 | 지령 변화율 분포 | 4.8 % (`r90`) |

지연이 줄지 않으면 원인이 태스크 구조가 아니라 `CMD_LPF`·`MOTOR_KP` 쪽이라는
뜻이다. 그쪽이 먼저일 수도 있다.

## 남은 판단

- 스트림 출력을 줄이는 것만으로 해결되는지 먼저 볼 것. 필드를 줄이거나
  `q` 로 끄거나 baud 를 460800 으로 올리면 61% 가 크게 떨어진다.
  **그것으로 충분하면 태스크 분리는 안 해도 된다.**
- 태스크로 쪼개면 디버깅이 어려워진다. 지금은 로그 한 줄로 전체 상태가
  보이는데, 비동기가 되면 그 스냅샷이 일관되지 않을 수 있다.
