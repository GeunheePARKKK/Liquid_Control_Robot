## 2. 구조 설계 — 안티슬로싱 제어 방식

### 참고 자료 조사

| 대상 | 결과 |
|---|---|
| HORIZON: Self-Balancing Tray (YouTube `Ej2z-kXA0-I`) | 설명란 비어 있음, 공개 코드 없음 |
| 물잔진동 제어 / 하이윈코리아 데모 | **리니어 스테이지 궤적 성형** 방식 (트레이 안 기울임) |
| 오픈소스 짐벌 | 대부분 서보 기반. BLDC 는 `Visaging/ESP32-Gimbal` (SimpleFOC) |

HORIZON 구조는 CAD 기준 **직교 2축 봉 + 볼베어링 패시브 짐벌 + 서보 능동 보정**의
하이브리드 방식.

### 핵심 결론: 수평제어와 안티슬로싱은 하나의 법칙

논문 Fig 3 의 합력 벡터가 두 경우를 모두 커버한다.

| 상황 | `a_linear` | `θ_ref` |
|---|---|---|
| 경사면 정지/정속 | 0 | 0 = 절대 수평 |
| 평지 가속 | ≠0 | 합력 방향 |
| 경사면 + 가속 | ≠0 | 자동 합성 |

**따라서 모드 분기(`if`)는 불필요하다.** 하드 스위칭은 오히려 위험하다.

- 경계 채터링 → 트레이가 덜컥거림 → 그 자체가 슬로싱 여기(excitation)
- ZV 버퍼에 과거 값이 남아 모드 진입 시 점프
- 논문 Fig 6(험지 주행)은 경사·가속이 **동시** 발생 — 어느 모드도 단독 처리 불가

### 채택할 구조

나눠야 할 기준은 원인이 아니라 **주파수**다. 경사는 저주파, 슬로싱은 약 2.4Hz.

```
setpoint (절대) = ZV( θ_관성 )      ← 성형 O, 안티슬로싱
feedback        = 트레이 IMU 절대각  ← 성형 X, 경사는 외란으로 즉시 제거
```

ZV 를 setpoint 경로에만 두면 경사 외란 제거는 지연 없이 동작하고,
가속 대응만 성형된다. 분기문 없이 목표한 2-모드 동작이 나온다.

### 기존 코드에서 발견된 문제

| 문제 | 내용 |
|---|---|
| roll 축에 ZV 미적용 | `shaped_roll = -roll_filtered` — `zv_buffer_x` 선언만 하고 미사용 |
| 데드존 동작 안 함 | LPF 계산 뒤에 `outputX = 0` → `filtered_outputX` 를 쓰므로 무효 |
| `error_deg_x` 에 setpoint 누락 | `error_deg_y` 와 형태 불일치 |
| X/Y 비대칭 | X 만 LPF 적용 |

## 3. 배선

### ESP32-S3 핀 배정

| GPIO | 대상 | 신호 |
|:---:|---|---|
| 4 / 5 | CAN 트랜시버 | TXD / RXD |
| 9 | 베이스 IMU | CS (미연결, 예약) |
| 10 | **트레이 IMU** | CS (10kΩ 풀업) |
| 11 / 12 / 13 | IMU 공통 | SDA(MOSI) / SCL(SCK) / SDO(MISO) |
| 17 / 18 | — | UART 예약 |

### 구형 ESP32 핀맵 무효화

이전 코드의 SPI 핀은 ESP32-S3 에서 사용 불가.

| 기존 | 문제 |
|---|---|
| `SDI_PIN = 23` | **S3 에 GPIO 22~25 자체가 없음** |
| `SDO_PIN = 19` | USB D− |
| `SCK_PIN = 18` | UART 로 재배정됨 |
| `CS 4, 5` | CAN 으로 재배정됨 |

상세는 [`hardware/배선도.md`](../../hardware/배선도.md).

## 4. IMU 코드 — `IMU_Reading.ino`

BMI160 → **LSM6DSOX** 전환에 따른 변경.

| 항목 | BMI160 | LSM6DSOX |
|---|---|---|
| 데이터 주소 | `0x0C` | `0x22` |
| WHO_AM_I | `0x00` → `0xD1` | `0x0F` → `0x6C` |
| **`GYRO_LSB`** | 16.4 | **14.286** |
| 전원 시퀀스 | `0x7E` 커맨드 반복 | `CTRL3_C` 리셋 1회 |

> `GYRO_LSB` 는 에러 없이 조용히 15% 틀리는 값이라 특히 주의.
> 16.4 는 ICM/MPU 계열 값이고 LSM6DSOX 는 70 mdps/LSB → 14.286.

## 5. 디버깅 이력 — IMU 값 이상

### 증상 1: `pitch_acc` 가 `0.00` / `35.26` 두 값만 출력

`arctan(1/√2) = 35.264°` 이므로 **ax = ay = az** 일 때만 나오는 값.
즉 포화가 아니라 **데이터가 아예 안 들어오는 상태**였다.

가속도계가 죽으면 상보 필터가 절대 기준을 잃고 순수 자이로 적분이 되어
각도가 365° 까지 발산 — 드리프트는 원인이 아니라 결과였다.

→ 배선 수정 후 해결.

### 증상 2: 잘 되다가 갑자기 깨짐

정지 상태에서는 `pitch` 와 `pitch_acc` 가 0.05° 이내로 일치했으나,
**움직이기 시작한 순간부터** 값이 깨짐. 설정 문제가 아닌 간헐적 오류.

대응으로 3가지 방어 로직 추가:

1. **부팅 진단** — WHO_AM_I / CTRL 레지스터 / raw 12바이트 덤프
2. **리셋 감지 및 복구** — `CTRL1_XL` 이 변하면 재초기화
3. **`|a|` 검사** — 1g 를 벗어난 샘플은 가속도 보정 제외

> 리셋 복구가 특히 결정적이었다. 이전에는 리셋 한 번에 센서가
> 파워다운으로 영구 방치되어 세션이 죽었다. (증상 1의 365° 발산이 그것)

### 증상 3: 거부 카운터 해석

`bit_err:1999/12323 (16.2%)` 가 통신 오류인지 실제 움직임인지 구분 불가.
카운터가 두 원인을 섞어 세고 있었다.

거부 **개수**보다 **연속 길이**가 중요하다. 샘플을 버리면 그 순간 자이로 단독
적분이 되는데, 흩어져 있으면 무해하고 뭉치면 각도가 틀어지기 때문. (1샘플 = 0.01초)

→ 연속 구간 추적 추가.

## 6. 벤치 테스트 결과 (측정 완료)

| 조건 | 결과 | 판정 |
|---|---|---|
| **정지** | 오류 **0 / 304** | 배선 정상 ✅ |
| 가볍게 움직임 | 최대연속 7~8 (0.08초) | 무해 ✅ |
| 격하게 흔듦 | 최대연속 **44** (0.44초), `\|a\|` **2.77g** | 문제 ❌ |

**정지 시 오류 0** — 이전의 16% 는 전부 실제 움직임이었고 하드웨어는 정상.

격한 동작에서 두 가지 문제 확인:

1. `|a| = 2.77g` → **±2g 범위 포화**
2. 0.44초 연속 무보정 → 자이로 단독 적분으로 `roll` 이 -103° 까지 붕괴

로봇 주행 시 출발·정지에서 동일 상황이 발생하므로 제어 진입 전 수정 필요.

## 7. 최종 반영 (`90e3c8c`)

### ① 측정 범위 ±2g → ±4g

```cpp
#define CTRL1_XL_VAL  0x68      // ±4g
const float G_LSB = 8192.0;
```

### ② 하드 컷 → 신뢰도 가중

버리면 연속 구간이 생기므로, 버리지 않고 **비중만 줄인다.**

```cpp
float dev   = fabsf(a_mag - 1.0f);
float trust = constrain(1.0f - dev / ACC_TRUST_FALLOFF, 0.0f, 1.0f);
float alpha = 1.0f - (1.0f - alpha_cf) * trust;

pitch_filtered = alpha*(pitch_filtered + rate_pitch*dt) + (1.0f-alpha)*pitch_acc;
```

| `\|a\|` | trust | 동작 |
|---|---|---|
| 1.00g | 1.00 | 평소대로 보정 |
| 1.25g | 0.50 | 절반만 반영 |
| 1.50g+ | 0.00 | 자이로 단독 |

가속 중에도 가속도계가 완전히 입을 다물지 않아 드리프트 누적이 줄어든다.

### ③ 진단 로그를 구간 기준으로

누적 표시는 한 번 튄 값이 계속 남아 "지금도 오류 중" 으로 오해된다.
직전 1초 구간 기준으로 바꾸고, 연속 길이는 최근/전체를 함께 표시.

```
[stat] reset:0  무보정:0/101  연속:0최근/44전체  |a|=1.01 trust=1.00
```

## 8. 모터 — `gimbal_control/motor_test.ino`

CAN 버스 짐벌모터 2개를 동일 목표로 왕복 구동.

| 모터 | CAN ID | Master ID |
|:---:|:---:|:---:|
| 1축 | `0x01` | `0x00` |
| 2축 | `0x02` | `0x01` |

**수신 프레임 구분 문제 수정** — 기존 코드는 도착한 프레임이 어느 모터 것인지
확인하지 않아 2축에서 값이 섞였다. `data[0] & 0x0F` (하위 4비트 = 모터 CAN ID)
로 구분하도록 변경.

상세는 [`gimbal_control/README.md`](../../gimbal_control/README.md).
