## 진단 도구 — `capture.py`

시리얼 모니터를 열지 않고 **명령 전송과 로그 수집을 한 번에** 하는 스크립트.
Claude Code 터미널에서 바로 돌리면 로그가 그대로 대화에 들어와 분석할 수 있다.

```
!python docs/CONTROL_INTEGRATION_TASK/capture.py --port COM14 --pre 5 --post 12 --out C:\arm_test.txt
```

| 인자 | 뜻 |
|---|---|
| `--port` | COM 포트 (장치관리자 또는 아두이노 IDE에서 확인) |
| `--pre` | 명령 전 관찰 시간 [초] |
| `--cmd` | 보낼 명령 (기본 `arm`, `t`, `none` 가능) |
| `--post` | 명령 후 기록 시간 [초] |
| `--out` | 저장 파일 |

동작 순서

```
pre초 관찰 → 명령 전송 → post초 기록 → stop 자동 전송 → 파일 저장
```

- 각 줄 앞에 **명령 시점 기준 상대시간**이 붙는다. 음수 = 명령 이전
- 끝나면 항상 `stop` 을 보내므로 모터가 켜진 채 방치되지 않는다
- **아두이노 시리얼 모니터를 반드시 닫고** 실행할 것 (포트는 하나만 점유 가능)

> Windows 콘솔(cp949)이 일부 문자를 못 찍어 예외가 나던 문제로 파일 저장이
> 통째로 날아간 적이 있어, 출력은 실패해도 무시하고 저장은 `finally` 로 옮겼다.

## 1. 최초 작성 (`35b67f5`)

### 목적과 범위

1단계로 **순수 수평제어만** 구현한다. 차체가 기운 만큼 트레이를 반대로 돌려
절대 수평을 유지하는 것까지.

```
motor_cmd = −θ_base
```

**이 단계에 넣지 않은 것** (다음 단계로 미룸)

| 항목 | 이유 |
|---|---|
| 합력 벡터 목표각 | 수평제어가 안정된 뒤 `θ_ref` 자리에 넣는다 |
| Convolved ZV 입력성형 | 위와 동일. 두 개를 동시에 켜면 원인 분리가 안 됨 |
| 상단(트레이) IMU | 제어에 쓰지 않는다. 성능 검증과 CNN 데이터 수집 전용 |

### 제어 구조 — 개루프 피드포워드

제어에 쓰는 센서는 **베이스(차체) IMU 하나뿐**이다. 트레이 IMU 는 루프에 없다.

```
베이스 IMU → 상보필터 → θ_base → (−1) → 슬루/제한 → CAN → 모터
                                                          ↑
                                              모터 내부 엔코더가 위치 루프를 닫음
```

이 구조를 택한 이유.

1. **진동하는 센서가 루프에 없다** — 트레이 IMU 는 짐벌 위에서 흔들린다.
   그 노이즈가 피드백에 들어가면 그대로 모터 지령이 된다.
2. **모터 엔코더가 이미 루프를 닫는다** — CAN 통합형이라 위치 제어는 모터
   내부에서 처리. IMU 로 유도한 각도보다 훨씬 깨끗하다.
3. **평가의 독립성** — 트레이 IMU 가 제어에 관여하면 "제어가 잘 됐는지" 를
   객관적으로 측정할 수 없다. 루프 밖에 있어야 독립적인 측정치가 되고
   CNN 학습 데이터도 오염되지 않는다.

한이음 보고서의 "Feed-forward Pre-emptive Control" 이 이 구조.

### 두 코드의 병합

| 출처 | 가져온 부분 |
|---|---|
| `IMU_Reading.ino` | SPI 읽기, 상보필터, 신뢰도 가중, 중력 정규화, 진단 |
| `motor_test.ino` | TWAI 초기화, `sendPosVel`, `sendUniversal`, 피드백 파싱 |

**신뢰도 가중을 그대로 유지한 이유** — 수평제어에도 필요하다. 차체가 가속하면
가속도계가 오염되어 `θ_base` 가 틀어지고, 그러면 트레이를 엉뚱한 방향으로
돌리게 된다.

### 모터 이름을 X/Y 대신 담당 각도로

```cpp
#define CAN_ID_PITCH  0x01
#define CAN_ID_ROLL   0x02
```

문서 간 대응이 **서로 반대**로 적혀 있어 X/Y 라는 이름 자체를 쓰지 않기로 했다.

| 출처 | Pitch | Roll |
|---|---|---|
| 논문 + 이전 구동 코드 | Y축 모터 | X축 모터 |
| 한이음 보고서 | Motor_X | Motor_Y |

실제 물리 모터가 반대로 물려 있으면 위 두 상수만 맞바꾸면 된다.

### 안전 설계

센서 입력으로 모터가 움직이는 첫 코드이므로 아래를 넣었다.

| 장치 | 값 | 목적 |
|---|---|---|
| **arm 필수** | 부팅 시 `0xFD` | 전원 인가만으로 움직이지 않게 |
| **GAIN** | 0.3 시작 | 방향이 반대여도 천천히 움직여 대응할 시간 확보 |
| 각도 제한 | ±25° | 기구 간섭 방지 |
| 슬루 제한 | 60 deg/s | 지령 급변 방지 |
| 속도 제한 | 2 rad/s | 모터 측 제한 |
| 자동 disarm | — | 센서 파워다운 / 무보정 1초 초과 / 모터 오류코드 |

가장 큰 위험은 **모터 방향이 반대인 경우**다. 기울어짐을 줄이는 게 아니라
키우는 양의 피드백이 되어 발산한다. GAIN 을 낮게 시작하고 슬루를 건 것이
이에 대한 대비.

`DIR_PITCH` / `DIR_ROLL` 을 `-1.0` 으로 바꾸면 해당 축 방향이 뒤집힌다.

### 시리얼 명령

| 명령 | 동작 |
|---|---|
| `arm` | 에러해제 → 영점 → enable |
| `stop` / `s` | disable |
| `z` | 현재 위치를 모터 영점으로 |
| `g<값>` | 게인 변경 (0.0 ~ 1.5) |
| `?` | 현재 상태 출력 |

### 출력 포맷

```
pitch:12.34,cmd_pitch:-3.70,roll:-5.21,cmd_roll:1.56
[stat] ARMED reset:0 무보정:0/200 |a|=1.00 trust=1.00
```

`cmd_*` 는 실제로 CAN 으로 내보낸 지령각. 시리얼 플로터로 `pitch` 와
`cmd_pitch` 를 겹쳐 보면 추종 상태를 바로 확인할 수 있다.

## 시운전 중 발견한 문제

### ① Enable 상태를 오류로 오판 (`0c82f2d`)

피드백 `data[0]` 상위니블은 **오류코드가 아니라 상태코드**다.
정상 동작 중이면 `1`(Enable) 이 온다.

```cpp
if (err != 0 && armed) motorsDisarm(...);   // Enable(1) 도 오류로 판정
```

arm → enable → 모터가 "Enable" 보고 → 즉시 disarm. **모터가 아예 안 움직였다.**
`motor_test.ino` 가 이 니블을 `err` 라는 이름으로 출력만 하고 있어서 그대로 믿고
안전장치를 붙인 것이 원인. 판정 기준을 `>= 0x8` 로 고쳤다.

### ② arm 순간 크게 튐 (`21dcbba`)

enable 전에 목표 위치를 지정하지 않아, 드라이버가 **마지막으로 기억하던 목표**로
달려갔다. 시험 구동(`t`) 직후면 그 값이 ±0.5 rad = ±28°.
GAIN 을 낮춰도 그대로였던 이유가 이것. enable 전에 목표=현재위치를 먼저 보낸다.

### ③ 밀린 주기 몰아치기 (`21dcbba`)

100Hz 를 `lastLoop += 10000` 으로 누적하는데, 시험 구동(6초)처럼 오래 걸리는
작업 뒤에는 밀린 600회가 순식간에 실행되며 자이로를 6초치 적분하고 CAN 을
수백 프레임 쏟아냈다. 0.1초 이상 밀리면 재동기하도록 변경.

### ④ 지령은 고정인데 모터가 왕복 (조사 중)

`capture.py` 로 12초 캡처한 결과, **지령은 완벽하게 안정적**이었다.

```
+0.27  cmd_pitch:-0.30     ← arm 직후, 0 에서 시작
+0.80  cmd_pitch:-16.58    ← 0.53초에 걸쳐 램프 (슬루 30°/s 대로)
+0.92 ~ +12.03             ← 이후 11초간 -16.58 ~ -16.67 (변동 0.09°)
```

계산도 정확했다. `pitch 55.27° × GAIN 0.3 = 16.58` → `cmd -16.58`.
IMU 도 정상 (`trust` 0.96~1.00, 무보정 0, 리셋 0).

그런데 **모터는 물리적으로 계속 왕복했다.** 지령이 고정인데 모터가 움직이므로
원인은 제어 코드 밖 — 드라이버 위치루프 또는 기구 쪽이다.

확인을 위해 추가한 것

- **모터 실제 위치 로깅** — 피드백 `data[1..2]` 를 각도로 변환해 `act_*` 로 출력.
  `cmd` 와 `act` 를 나란히 보면 진동의 진폭과 주기를 잴 수 있다.
- **CAN 전송 분주 (`CAN_DIV`)** — 위치/속도 모드 드라이버는 프레임을 받을 때마다
  내부 궤적을 새로 시작할 수 있다. 같은 목표를 100Hz 로 재전송하면 계속
  재시작하며 떨 수 있으므로 기본을 50Hz(`d2`)로 낮췄다.
  `motor_test.ino` 가 문제없던 주기가 50Hz 였다.
- 출력 주기를 10Hz → 50Hz 로 올려 진동을 관찰할 수 있게 했다.

## 시운전 결과

아래 순서로 진행하고 결과를 기록할 것.

| 단계 | 확인 항목 | 결과 |
|---|---|---|
| 1 | 모터 없이 부호 확인 — `pitch` 와 `cmd_pitch` 가 반대 부호인가 | (미실시) |
| 2 | 모터 방향 — 트레이가 반대로 돌아 수평을 유지하는가 | (미실시) |
| 3 | 게인 상승 — 어느 GAIN 에서 진동이 시작되는가 | (미실시) |
| 4 | 정량 확인 — 20° 기울일 때 GAIN 1.0 에서 수평이 유지되는가 | (미실시) |

> 2단계 확인 전에는 GAIN 을 올리지 말 것. 방향이 반대면 발산한다.

### 기록할 항목

- `DIR_PITCH` / `DIR_ROLL` 최종 부호
- 진동 없이 쓸 수 있는 최대 GAIN
- 필요했던 `VEL_LIMIT` / `MAX_RATE` 조정값
- 20° 기울임에서의 트레이 실제 각도 (각도기 또는 상단 IMU)
