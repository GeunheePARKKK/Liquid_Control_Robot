## 왜 수평이 정답이 아닌가

가속하는 차 안의 물컵을 생각하면 된다. 컵을 수평으로 붙잡고 있으면 물은
뒤로 쏠린다. 액체 입장에서는 중력과 관성력의 **합력**이 진짜 아래쪽이므로,
컵 바닥을 그 합력에 수직으로 놓아야 수면이 컵 기준으로 평평해진다.

| 상황 | 합력 | θ_ref |
|---|---|---|
| 정지·등속 | 중력만 | **0** — 수평이 정답 |
| 가속 중 | 중력 + 관성력 | **≠0** — 기울여야 정답 |
| 경사면 + 가속 | 둘의 합 | 자동으로 합성 |

**수평제어와 안티슬로싱이 별개의 모드가 아니다.** 한 식이 두 경우를 모두 덮는다.
경사면에 서 있으면 `a_linear` 가 0 이라 `θ_ref` 도 0 이 되어 자동으로 절대 수평이 된다.

> 초기에 "1. 수평제어 / 2. 안티슬로싱" 으로 모드를 나누려 했으나 그렇게 하면
> 경계에서 채터링이 생기고, 그 덜컥거림 자체가 슬로싱을 새로 만든다.
> 험지 주행처럼 경사와 가속이 동시에 오는 상황도 어느 모드로도 처리가 안 된다.

## 무엇이 바뀌었나

1단계에서 **목표각 한 항만** 추가됐다.

```
1단계 :  θ_ref = 0                    →  motor_cmd = −θ_base
2단계 :  θ_ref = atan(a_linear / g)   →  motor_cmd = θ_ref − θ_base
```

### 계산 순서

```cpp
// 1. 중력 성분 제거 — 가속도계는 기울어져 있기만 해도 중력을 읽는다
float one_g   = G_LSB * g_scale;
float a_lin_y = ay - one_g * sinf(pitch_filtered * DEG_TO_RAD);
float a_lin_x = ax - one_g * sinf(roll_filtered  * DEG_TO_RAD);

// 2. 합력이 수직에서 벗어난 각도
float raw_ref_p = atan2f(a_lin_y, one_g) * RAD_TO_DEG * DIR_ACC;

// 3. 노이즈가 크므로 목표각을 따로 저역통과
ref_pitch = ACC_LPF * raw_ref_p + (1 - ACC_LPF) * ref_pitch;

// 4. 모터는 차체 기준으로 도므로 차체 자세를 뺀다
want_pitch = (ACC_GAIN * ref_pitch - pitch_filtered * GAIN) * DIR_PITCH;
```

중력을 뺄 때 쓰는 각도가 1단계에서 만든 `θ_base` 다. `g_scale` 은 부팅 시
정규화한 값이라 1g 에 해당하는 LSB 가 `G_LSB × g_scale` 이다.

### 새 파라미터

| 이름 | 기본 | 명령 | 뜻 |
|---|---|---|---|
| `ACC_GAIN` | **0** | `ag<값>` | 합력 항 게인. **0 이면 1단계와 완전히 동일** |
| `DIR_ACC` | +1 | (코드) | 합력 목표각 부호. 실측으로 정함 |
| `ACC_LPF` | 0.2 | `ad<값>` | θ_ref 전용 저역통과 |
| `ACC_REF_LIMIT` | 20° | (코드) | θ_ref 자체의 상한 |

### 출력에 `ref_*` 추가

```
pitch:12.34,ref_pitch:-4.20,cmd_pitch:-12.10,act_pitch:-11.8,roll:...
                  ↑ 합력 목표각
```

`ACC_GAIN` 이 0 이어도 계산되어 찍힌다. **모터를 켜지 않고 부호를 확인**할 수 있다.

---

## 기본값을 0 으로 둔 이유

부호가 반대면 가속할 때 액체를 **더** 흔드는 쪽으로 기울인다.

수평제어는 부호가 틀리면 트레이가 반대로 기우는 것이 바로 보인다. 그런데
합력 항은 **가속하는 순간에만** 나타나므로 눈으로 알아채기 어렵다.
그래서 처음 올리면 1단계와 똑같이 동작하게 두고, 숫자로 확인한 뒤 켠다.

되돌릴 때도 `stop` 보다 **`ag0`** 이 먼저다. 수평제어는 계속 살아 있다.

## 부호 확인 절차

### 1) 모터 없이 부호만

`arm` 하지 않고 IMU 를 책상에서 한 방향으로 민다. `ref_pitch` 를 본다.

| 보드 **+Y 방향**으로 밀었을 때 | 판정 |
|---|---|
| `ref_pitch` 음수 | ✅ 맞다 (`DIR_ACC = +1` 유지) |
| `ref_pitch` 양수 | ❌ `DIR_ACC` 를 `−1` 로 |

음수여야 하는 이유. 컵을 +Y 로 가속하면 물은 −Y 로 쏠린다. 수면을 컵 기준으로
평평하게 두려면 컵의 +Y 쪽을 내려야 한다. 우리 규약에서 `+pitch` 는 +Y 가
올라가는 것이므로 목표는 음수가 된다.

roll 은 `+roll` 이 +X 가 **내려가는** 것이라 부호 방향이 pitch 와 반대다.

### 2) 정지 상태 확인

- 책상에 가만히 → `ref` 가 0 근처
- **기울여 놓고 가만히 → 이때도 0 근처**

기울기만으로 `ref` 가 생기면 중력 제거가 잘못된 것이다. `g_scale` 과 `θ_base`
를 먼저 의심한다. **이 경우 `ACC_GAIN` 을 올리면 안 된다.**

### 3) 게인 상승

```
ag0.3  →  ag0.6  →  ag1.0
```

각 단계에서 IMU 를 밀었다 세웠다 하며 트레이가 가속 반대쪽으로 기우는지 본다.

### 기록할 것

| 항목 | 값 |
|---|---|
| `DIR_ACC` 최종 부호 | `+1` (물리 부호는 식에 내장) |
| 정지 시 `ref` 편차 | 0 근처 — 평평·경사 모두 확인 |
| 안정적인 최대 `ACC_GAIN` | (미측정) |
| `ACC_LPF` 적정값 | (미측정) |

## 아직 없는 것

**ZV 입력성형이 없다.** 지금은 `θ_ref` 가 바뀌는 즉시 그대로 따라가므로,
목표각의 급변 자체가 슬로싱을 새로 만들 수 있다. 3단계에서 `θ_ref` 에
Convolved ZV 를 걸어 그 성분을 없앤다.

**지연이 150~180ms 로 측정돼 있다.** 슬로싱 주기 420ms 의 36% 라 위상 여유가
부족하다. `CMD_LPF`(57ms)·슬루·낮은 `Kp` 가 원인이며, 3단계 전에 손봐야 할 수 있다.

## 부호를 두 번 틀린 기록

두 축의 각도 정의가 반대라는 사실이 두 곳에서 각각 터졌다. 같은 원인인데
증상이 달라서 한 번에 못 잡았다.

```
pitch 는  atan2( ay, ...)  로,   roll 은  atan2(-ax, ...)  로 정의했다
```

### 1차 — 중력 제거 부호

`c43658f` · 2026-08-29 22:47

중력 성분을 두 축 다 빼도록 썼다.

```cpp
a_lin_y = ay - one_g * sin(pitch);   // 맞음
a_lin_x = ax - one_g * sin(roll);    // 틀림
```

`roll` 규약에서는 `ax = −g·sin(roll)` 이라 중력 몫이 이미 음수다. 여기서 또
빼면 상쇄가 아니라 **두 배**가 된다.

증상이 명확했다. 평평하게 두었는데 실제 `roll` 이 2.5° 였을 때:

```
ax       = −g·sin(2.5°) = −0.0436 g
a_lin_x  = −0.0436g − 0.0436g = −0.0872 g      ← 두 배
ref_roll = atan(−0.0872) = −5.0°               ← 실측과 일치
```

조금만 기울여도 `ACC_REF_LIMIT` 20° 에 포화됐다. `ref_pitch` 는 멀쩡했고,
그 비대칭이 식이 아니라 축을 가리켰다.

**정지 상태 확인 절차가 잡아낸 것이다.** 가속 시험부터 했으면 `ref_roll` 이
이미 포화돼 있어 부호 판정 자체가 불가능했다.

### 2차 — 목표각 부호

`d98757d` · 2026-08-29 23:06

`DIR_ACC` 하나를 두 축에 공유했다. 그런데 축마다 필요한 부호가 다르다.

가속도계는 비력 `f = a − g` 를 읽는다. 평평한 상태에서 `+Y` 로 `A` 만큼
가속하면 `ay = +A` 다.

| 축 | 코드 결과 | 있어야 할 값 | 판정 |
|---|---|---|---|
| pitch | `+atan(A/g)` | `−atan(A/g)` | ❌ 반대 |
| roll | `+atan(A/g)` | `+atan(A/g)` | ✅ 맞음 |

`−atan(A/g)` 인 이유. 유효중력이 `(0, −A, −g)` 라 트레이 법선은 `+Y` 쪽으로
기울어야 하고, 그것은 `+Y` 모서리가 **내려간다**는 뜻이다. 우리 규약에서
`+pitch` 는 `+Y` 가 올라가는 것이므로 목표각은 음수다.

**정지 상태로는 절대 안 보인다.** 가속할 때만 나타나고, 밀기와 멈추기가 항상
쌍으로 나와 로그의 부호만 봐서는 구분되지 않는다. 유도로 잡았다.

### 고친 방식 — 축마다 부호를 두지 않는다

`roll` 의 가속도 성분을 처음부터 `−ax` 로 잡아 두 축을 같은 식으로 만들었다.

```cpp
float acc_p =  (float)ay;     // pitch 규약
float acc_r = -(float)ax;     // roll  규약  ★ 각도 정의와 동일

float p_lin = acc_p - one_g * sinf(pitch_filtered * DEG_TO_RAD);
float r_lin = acc_r - one_g * sinf(roll_filtered  * DEG_TO_RAD);

float raw_ref_p = -atan2f(p_lin, one_g) * RAD_TO_DEG * DIR_ACC;
float raw_ref_r = -atan2f(r_lin, one_g) * RAD_TO_DEG * DIR_ACC;
```

중력 제거도 목표각도 두 축이 대칭이라 규약을 틀릴 자리가 한 곳뿐이다.
앞의 `−` 는 물리(가속 반대쪽으로 기운다)이고, `DIR_ACC` 는 실측용 뒤집기로
`+1` 에 남겼다.

신호는 노이즈가 아니다. 5.0초 부근 파형:

```
5.00  +14.41
5.05  +17.14     ← 양의 피크 (밀기 시작, 가속)

5.12   -7.60
5.17  -16.70     ← 음의 피크 (멈추기, 감속)
5.23   -3.95
```

**양 피크 → 음 피크 쌍**이 0.2초 간격으로 반복된다. 밀고 멈추는 동작의
교과서적 신호다. 크기 17° 는 0.3g 에 해당한다.

이 쌍 구조 때문에 로그만으로는 부호를 못 가린다. 한 번 밀 때마다 양수와
음수가 모두 나오므로, 어느 쪽이 "미는 순간"인지 알려면 민 방향을 알아야 한다.
2차 부호 문제를 유도로 잡은 이유가 이것이다.
