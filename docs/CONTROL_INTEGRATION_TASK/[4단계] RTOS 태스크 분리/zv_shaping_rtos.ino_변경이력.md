## 절대 규칙

> **제어 수식, 명령어, 출력 내용을 바꾸지 않는다. 실행 구조만 바꾼다.**

계산식은 복사만 했다. 손으로 다시 쓰지 않았다.

검증은 두 가지로 했다.

**① 문자열 전수 대조** — 두 파일의 리터럴을 모두 뽑아 비교했다.

```
3단계 131종 137개  /  4단계 137종 143개
사라진 출력 : 0건
새 문자열   : "%s\n"(qprintln 내부)  "ctrl"  "io"  그리고 [rtos] 계측 줄 2개
```

**② 삭제된 코드 줄 전수 확인** — 들여쓰기·주석을 무시하고 원본에서 없어진 줄을
전부 뽑았더니 아래 6가지뿐이었고, **제어 수식 줄은 하나도 없었다.**

| 없어진 줄 | 수 | 왜 |
|---|---|---|
| `float GAIN = ...` 등 선언 | 17 | `volatile` 이 붙음 |
| `Serial.printf` / `println` | 13 | `qprintf` / `qprintln` 로 (내용 동일) |
| `arm` `stop` `t` `z` 처리 | 7 | 요청 큐로 |
| `float &d = ...` | 1 | `volatile float &d` |
| `zvRecalc(); zvClear();` | 4 | 잠금 추가 |
| `loop()` 머리 + 스트림 printf | 15 | `vTaskDelayUntil` + 스냅샷 큐 |

## 무엇이 바뀌었나

```
3단계                          4단계
loop() {                       ctrl (코어1, 우선순위6)   io (코어0, 우선순위2)
  handleSerial()                 vTaskDelayUntil(10ms)     큐에서 꺼내 출력
  10ms 지났나?                   요청 실행 (arm/stop/t/z)   handleLine()
  IMU→필터→ZV→제어→CAN           IMU→필터→ZV→제어→CAN
  로그 출력                      숫자만 큐에 ──────────────→
}                              loop() = vTaskDelay(1000)  껍데기
```

`ctrl` 본문의 순서는 3단계 `loop()` 와 같다.
`readIMU` → 상보필터 → 이상감지 → `drainCAN` → 합력벡터 → ZV → 제어 →
`sendBoth` → 출력 → 2초 상태.

`loop()` 를 지우지 않은 이유는 아두이노 `loopTask` 가 태스크 워치독에게 살아있다고
보고하는 역할을 겸하기 때문이다. 지우면 리셋이 걸릴 수 있어 껍데기로 남겼다.

### `dt` 가 가정에서 약속으로

`const float dt = 0.01;` 을 상보필터와 슬루(`MAX_RATE * dt`)가 쓴다.
3단계에는 그것을 보장하는 장치가 없었다 — 안 늦었을 뿐이다.
`vTaskDelayUntil` 은 OS 가 지킨다.

## 나누면서 생긴 위험 6가지 — 전부 막았다

**RTOS 자체의 문제가 아니다.** 일이 한 줄로 서 있으면 원리적으로 불가능했던 일들이
두 줄로 나누면 가능해진다. 그 "가능해진 것"이 위험이다.

```
3단계    A가 끝나야 B가 시작   →  둘이 부딪힐 수가 없다
4단계    A와 B가 진짜 동시에   →  부딪힐 수 있다
```

그래서 나누기 전에 여섯 곳을 막아야 했다. **여섯 개가 남아 있는 것이 아니라,
여섯 개를 찾아서 막았고 실기로 확인했다는 뜻이다.**

| # | 나누면 가능해지는 일 | 막은 장치 | 실기 확인 |
|---|---|---|---|
| ① | 두 태스크가 동시에 `Serial` 에 써서 줄이 섞인다 | 큐 2개, `io` 만 `Serial` 을 만진다 | 태스크 경합으로 인한 섞임 0건 |
| ② | `arm` 250ms 동안 제어 지령이 계속 나간다 | 명령 큐 + `ctrlBusy` | `arm` 중 지령 없음, `재동기 1` |
| ③ | ZV 계수 4개가 섞인 조합으로 읽힌다 | 스핀락 `zvMux` | `zd` 응답의 `A1/A2/A3` 가 3단계와 동일 |
| ④ | 시리얼 파서가 최대 1초 막혀 큐가 넘친다 | 문자 단위 비동기 파서 | `샘플드롭 0` |
| ⑤ | 밀린 틱을 간격 없이 몰아서 실행한다 | 매 틱 끝에서 재동기 | `10ms초과 0` |
| ⑥ | IDLE 태스크가 굶어 워치독이 리셋한다 | 반드시 기다리는 함수만 사용 | 26초 연속 구동 중 리셋 0 |

①②③④는 **코드 리뷰에서 지적받아 고친 것**이다. 처음 구현에는 `pendingCmd` 변수
유실, sweep 중 설정 변경, `zv1` 의 락 밖 대입, `readStringUntil` 블록이 실제로
남아 있었다. 아래에 각각 어떤 상태였고 어떻게 바꿨는지 적는다.

### ① 동시 출력 → 줄이 섞인다

**3단계에서는 불가능했다.** 출력하는 곳이 `loop()` 한 군데뿐이었다.

**안 막으면** 이렇게 된다.

```
정상 : t:123,pre_pitch:6.28,...,cmd_pitch:6.28
섞임 : t:123,pre_p!! 모터 이상itch:6.28,...
```

`check_tuning.py` 는 한 줄 안에서 `pre_pitch` 와 `cmd_pitch` 를 짝지어 읽는다.
줄이 깨지면 분석이 무너진다.

**막은 방법.** `Serial` 은 `io` 태스크만 만진다. `ctrl` 은 큐에 넣고 지나간다.
함수별로 전수 감사해 `ctrl` 쪽 출력 13곳을 `qprintf` / `qprintln` 으로 바꿨다.

```cpp
QueueHandle_t qEvt  = NULL;     // 텍스트 12통  — 모터이상·폭주차단·두절·DISARM 이유
QueueHandle_t qSnap = NULL;     // 샘플 32통   — 33Hz 스트림
```

**큐를 두 개로 나눈 이유가 따로 있다.** 하나로 두면 PC 가 멈춘 순간 샘플이 자리를
먼저 차지해서 **정작 원인이 되는 이벤트가 버려진다.** 제어는 돌아도 사후 분석이
막힌다. `io` 는 `qEvt` 를 먼저 비운다.

스트림은 **숫자만** 큐에 넣는다. `%.2f` 13개 포맷(수백 µs)은 `io` 가 진다.

`ctrl` 쪽 출력은 **대기 0** 이다. 처음에는 5ms 를 기다리게 했는데, PC 가 안 읽어서
큐가 차면 로그 한 줄마다 제어가 멈춘다 — 그걸 없애려고 나눈 것이라 앞뒤가 안 맞았다.
리뷰 지적으로 0 으로 바꿨다. 잃은 줄은 `dgEvtDrop` 으로 센다.

> **남은 것.** 태스크 경합은 없앴지만 USB 계층에서 0.45% 가 깨진다.
> 원인 미확정. [README 의 「아직 안 된 것」](README.md#usb-로그-줄-깨짐-045) 참고.

### ② `arm` 은 250ms, `t` 는 8초 블록한다  ← 제일 위험했다

```cpp
broadcastUniversal(0xFB);  delay(50);   // 에러 해제
broadcastUniversal(0xFE);  delay(50);   // 영점
sendBoth();                delay(50);
broadcastUniversal(0xFC);  delay(100);  // enable
```

**3단계에서는 이 250ms 동안 제어도 같이 멈춰 있었다.**

**안 막으면** — `io` 에서 실행하면 그동안 `ctrl` 이 CAN 지령을 계속 쏜다.
**영점을 재정의하는 중에 지령이 끼어든다.** 3단계에서는 물리적으로 불가능한
상황이고, 모터가 어디로 갈지 모른다. `motorsArm()` 은 I2C 도 쓰는데 `Wire` 는
두 태스크가 동시에 만지면 깨진다.

**막은 방법.** 요청 큐로 넘기고 `ctrl` 이 직접 실행한다. 같은 코드가 같은 것을
멈춘 채로 돌아서 3단계와 동작이 같아진다.

```cpp
QueueHandle_t qCmd = NULL;        // 명령 6통
volatile bool ctrlBusy = false;   // arm / t 실행 중
```

여기서 세부 세 가지를 리뷰에서 지적받아 고쳤다.

| 처음 구현 | 무엇이 잘못됐나 | 고친 것 |
|---|---|---|
| `volatile uint8_t pendingCmd` 변수 하나 | `ctrl` 이 읽고 지우는 사이에 들어온 명령이 사라지고, 연속 입력은 앞의 것을 덮어쓴다 | **큐** 로 바꿨다. `stop` 은 자리가 없으면 앞 명령을 하나 버려서라도 넣는다 |
| 명령 처리 뒤 공통으로 `ctrlBusy = false` | 큐에 `[z, arm]` 이 있으면 `z` 가 먼저 풀어버려 arm 250ms 동안 파서가 다시 열린다 | **`arm` 과 `t` 가 끝날 때만** 푼다 |
| `ctrlBusy = true; ctrlSend(1);` | 큐에 못 넣으면 풀어줄 사람이 없어 파서가 영영 멈춘다 | `ctrlSend` 를 `bool` 로 바꿔 **실패하면 되돌린다** |

**`ctrlBusy` 를 "차단" 이 아니라 "파서 정지" 로 한 이유.** 3단계는 sweep 8초 동안
`handleSerial()` 이 아예 안 불려서, 입력이 UART 버퍼에 쌓였다가 끝난 뒤 처리된다.
`ctrlBusy` 중 `Serial.read()` 를 하지 않으면 바이트가 그대로 남아 **동작이 정확히
같아진다.** 거부하거나 따로 보관하는 것보다 정확하다.

이걸 안 막으면 sweep 도중 `dr` 이 들어와 복귀 직후 roll 방향이 뒤집힌다.
출력 순서 문제가 아니라 모터가 달라지는 문제였다.

### ③ ZV 계수는 4개가 한 세트다

```cpp
void zvRecalc() {
  zv_n1 = ...;   // 반주기 [샘플]
  zv_A1 = ...;   // 임펄스 진폭
  zv_A2 = ...;
  zv_A3 = ...;
}
```

**안 막으면** `ctrl` 이 바꾸는 도중에 읽는다.

```
zv_A1 = 새 값,  zv_A2 = 옛 값   ← 섞인 조합
→ 그 틱만 엉뚱한 성형을 한다
```

`zvClear()` 는 링버퍼 float 256개를 지우므로 반만 지워진 것을 읽을 수도 있다.

**막은 방법.** 스핀락. `zvRecalc` · `zvClear` · `ctrl` 의 ZV 계산 블록 세 곳이다.

```cpp
portMUX_TYPE zvMux = portMUX_INITIALIZER_UNLOCKED;
```

**처음 구현에서 `zv1` 하나가 빠져 있었다.** 리뷰 지적으로 고쳤다.

```cpp
ZV_ON = ...;                                    // 락 밖 — 그 사이 한 틱이 지나간다
if (ZV_ON) { ZV_LOCK(); zvClear(); ZV_UNLOCK(); }
```

```cpp
bool zvOn = (s.substring(2).toInt() != 0);      // 변환은 락 밖에서 먼저
ZV_LOCK();
ZV_ON = zvOn;
if (zvOn) zvClear();
ZV_UNLOCK();
```

문자열 변환을 락 밖으로 뺀 것도 의도적이다. 임계구역 안에서 `String` 을 만들면
**인터럽트가 막힌 채로 힙을 건드린다.**

`zf` `zd` `zm` 은 처음부터 변경 전체를 잠갔다. 요청 큐 대신 락을 쓴 이유는 `zd` 가
계산 직후 `A1/A2/A3` 를 바로 찍기 때문이다 — 미루면 옛 값이 찍혀 출력이 달라진다.

**반면 홑겹 변수는 막을 필요가 없다.** `GAIN` `MOTOR_KP` `MAX_RATE` `ZV_ON`
`stream` 등은 32비트 단일 접근이 원자적이라 옛 값 아니면 새 값이지 섞인 값이
안 나온다. `volatile` 만 붙였다. `dp`/`dr` 의 `float &d` 는 `volatile float &d`
로 바꿔야 컴파일된다.

### ④ `readStringUntil` 은 최대 1초 막힌다

```cpp
String s = Serial.readStringUntil('\n');   // 개행이 안 오면 기본 1초 대기
```

**3단계에서는 이래도 됐다.** 막히면 전체가 같이 멈추니 잃는 것이 없었다.

**안 막으면** — `io` 가 그 1초 동안 큐를 못 비운다. **32칸 샘플 큐는 33Hz 에서
1초면 찬다.** 터미널이 `k` `p` `2` 를 나눠 보내기만 해도 로그가 통째로 날아간다.

**막은 방법.** 문자 단위 비동기 파서. `handleSerial()` 을 `handleLine(const char*)`
로 바꿨고, 명령·응답 내용은 그대로다.

```cpp
while (!ctrlBusy && Serial.available()) {
  char c = Serial.read();
  if (c == '\n' || c == '\r') { if (n) { line[n] = 0; n = 0; handleLine(line); } }
  else if (n < sizeof(line) - 1) line[n++] = c;
}
```

`'\r'` 도 종결로 본다. 3단계는 `readStringUntil('\n')` 뒤에 `trim()` 을 했으니
결과가 같다.

### ⑤ 밀린 틱을 몰아서 실행한다

**처음 구현은 `arm`/`t` 뒤에만 시계를 맞췄다.** 리뷰에서 이것으로 부족하다는
지적을 받았다.

`configSensor()` 는 **명령이 아니라 센서 이상 감지에서 자동으로 불리고**, 정상
실행만으로 150ms 를 쓴다.

```cpp
writeReg(REG_CTRL3_C, 0x01);  delay(50);    // 소프트 리셋
...                           delay(100);
```

I2C 가 응답 없으면 여기에 최대 50ms 가 더 붙는다.

**안 막으면** `vTaskDelayUntil` 이 밀린 틱을 **10ms 간격 없이 연속으로 따라잡는다.**
제어 계산과 CAN 전송이 한꺼번에 몰린다.

**막은 방법.** 특정 명령 뒤가 아니라 **매 틱 끝에서** 실제 지연을 검사한다.

```cpp
if ((TickType_t)(xTaskGetTickCount() - xLastWake) >= pdMS_TO_TICKS(20)) {
  xLastWake = xTaskGetTickCount();
  dgResync = dgResync + 1;
}
```

계측 시작점도 명령 처리 **뒤**로 옮겼다. `arm` 의 의도된 250ms 정지를 같이 세면
(실측 270,621 µs 로 찍혔다) 정작 제어 틱이 늦었는지를 볼 수 없다.

### ⑥ 바쁜 대기는 워치독 리셋을 부른다

FreeRTOS 워치독은 어떤 태스크가 CPU 를 놓지 않으면 죽은 것으로 보고 **보드를
리셋한다.** 3단계에는 태스크가 하나였으니 해당이 없었다.

```cpp
while (!Serial.available()) { }     // ← 이렇게 짜면 리셋된다
```

**막은 방법.** 둘 다 반드시 기다리는 함수를 쓴다.

- `ctrl` → `vTaskDelayUntil(&xLastWake, pdMS_TO_TICKS(10))`
- `io`   → `xQueueReceive(qSnap, &sn, pdMS_TO_TICKS(5))`

아두이노 `loopTask` 도 지우지 않고 `vTaskDelay(1000)` 껍데기로 남겼다. 이 태스크가
워치독에게 살아있다고 보고하는 역할을 겸한다.

## 실측값을 기본값으로

3단계 기본값은 매번 손으로 넣어야 해서 빠뜨리는 사고를 두 번 겪었다.
시리얼 명령으로 여전히 바꿀 수 있다.

| 항목 | 3단계 | 4단계 | 근거 |
|---|---|---|---|
| `MAX_RATE` | 30 | **120** | 요구 변화율 p95 가 101~112 °/s. 30 이면 지령의 31% 가 잘려 ZV 성형이 무너진다 |
| `MOTOR_KP` | 1.0 | **2.0** | 드룹 54~82% → 89% |
| `MOTOR_KD` | 0.13 | **0.13** | `Kd ∝ √(Kp+k)`, `k ≈ 0.28 N·m/rad` |

`k` 는 트레이 무게중심이 축보다 아래에 있어 생기는 복원 강성이다.
정지 구간에서 `act/cmd` 가 일정 비율로 모자란 것(오프셋 −0.38°/+0.10°, 거의 0)에서
`k = Kp·(1/droop − 1)` 로 냈다. 마찰이면 비율이 아니라 고정 오프셋으로 나타난다.

### ZV 성형은 슬루를 더 걸지 않는다

같은 로그에서 ZV 만 뺀 반사실 계산을 돌렸다 (`ref_*` 와 `zv_*` 가 둘 다 기록돼 있다).

| | ZV 끔 | ZV 켬 |
|---|---|---|
| pitch 슬루 걸림 | 10.8% | 10.9% |
| roll 슬루 걸림 | 12.3% | **10.0%** |
| roll 요구 p95 | 133 °/s | **122 °/s** |

임펄스 합이 1이고 둘 다 양수라 **가중 이동평균**이다. 계단이 하나 늘지만 각 계단
높이가 절반이라 최대 변화율은 오히려 내려간다.
(절대값은 33Hz 로그를 100Hz 로 재구성한 탓에 부풀려져 있다. 차이만 유효하다.)

## 슬루 판정용 필드

출력 앞에 세 개를 붙였다.

```
t:23561,pre_pitch:-2.62,pre_roll:-8.91,pitch:2.36,ref_pitch:0.82,zv_pitch:0.82,...
```

| 필드 | 왜 |
|---|---|
| `t` | 펌웨어 시각. PC 수신 시각에는 USB 지터가 섞여 변화율 계산에 못 쓴다 |
| `pre_*` | 슬루 **걸기 전** 지령(`lpf_*`). `cmd` 와 다르면 잘린 것이고, 차이가 잘려나간 양이다 |

`cmd` 만 보면 잘린 흔적이 이미 지워져 알 수가 없다. `MAX_RATE = 120` 을 고른
근거가 이 `pre_*` 에서 나왔다.

기존 `ref_*` · `zv_*` 는 그대로다. 새 변수를 만든 게 아니라 이미 있는 `lpf_*` 를
출력에 실었을 뿐이라 제어 계산은 한 줄도 안 바뀌었다.

주기는 조건이 `> 20` 이라 10ms 루프에서 **30ms** 마다 나간다. 33Hz 다 (주석의 50Hz 수정).

## CAN 송신 대기 0

```cpp
if (twai_transmit(&m, 0) != ESP_OK) dgTxFail = dgTxFail + 1;   // sendMIT
```

`sendMIT` 은 50Hz 로 계속 나가는 주기 지령이라 한 장 버려도 20ms 뒤 다음 장이 간다.
반면 5ms 를 기다리면 두 축이 10ms — **한 틱 예산 전부**다.

**실측 근거.** 모터 전원을 끈 채 `arm` 하면 CAN ACK 가 없어 송신 큐가 막힌다.

| | 5ms 대기 | 대기 0 |
|---|---|---|
| `10ms초과` | **17** | **1** |
| `TX실패` | 36 | 36 |

실패 **횟수**는 같고 **대기 시간**만 사라진다 (송신 큐 5칸이 차면 그 뒤는 어차피 실패).
정상 CAN 에서는 큐가 안 차므로 `TX실패 0` 이고 동작이 같다.

남은 1건은 `motorsDisarm` 의 `broadcastUniversal(0xFD)` 다. `sendUniversal` 은
비주기 명령이라 **한 장이 중요해서 5ms 를 그대로 뒀다.** 2축 × 5ms + 1ms = 11.0ms 이고
실측 11,023 µs 와 맞는다. CAN 이 이미 죽었을 때 정지하는 순간 한 번이라 그대로 둔다.

## 실기 검산

`RTOS_DIAG` 계측을 넣고 실기에서 확인했다.
`t:` 간격만으로는 100Hz 누락을 못 잡는다 — 출력 게이트가 틱 안에 있어서
**틱 하나가 빠져도 앞뒤 출력이 30ms 로 보인다.** 그래서 틱 자체를 쟀다.

### 모터 전원 OFF, arm 안 함

```
최대틱 490~630us   10ms초과 0   재동기 0   TX실패 0   드롭 전부 0
```

### 모터 전원 ON, `arm`, 26초 캡처

```
최대틱 550~593us   10ms초과 0   재동기 1   TX실패 0   드롭 전부 0
피드백 2523회 (100/s = 50Hz × 2축)
```

`재동기 1` 은 `arm` 의 `delay` 250ms 때 한 번이다. 설계대로다.
계측 시작점을 명령 처리 **뒤**로 두었다. `arm` 의 의도된 정지를 같이 세면
(실측 270ms 로 찍혔다) 제어 틱이 늦었는지를 볼 수 없다.

### 3단계 로그와 비교

같은 도구(`capture.py` → `check_tuning.py`)로 같은 조건에서 비교했다.

| | 3단계 | 4단계 |
|---|---|---|
| pitch 드룹 | 89% | **89%** |
| pitch 추종오차 RMS | 3.31° | 3.18° |
| pitch 슬루 걸림 | 6% | 4% |
| roll 슬루 걸림 | 7% | 6% |
| pitch 요구 p95 | 101 °/s | 96 °/s |

**드룹이 정확히 같다.** 나머지 차이는 흔든 세기 차이다 (요구 변화율이 전반적으로
낮다 = 덜 세게 흔들었다). roll 드룹과 떨림은 계속 흔들어 정지 구간이 없어서
안 나왔다 — 다음에는 흔들다가 2초쯤 멈추기를 서너 번 섞어야 한다.

### 피드백 두절 워치독

모터 전원 없이 `arm` 했을 때 **302ms 만에 스스로 내려갔다.**

```
>>> ARMED  GAIN=1.00  ACC_GAIN=1.00  Kp=2.0  Kd=0.13  제한 ±25°
!! 피드백 302ms 끊김
>>> DISARM — 피드백 두절
```
