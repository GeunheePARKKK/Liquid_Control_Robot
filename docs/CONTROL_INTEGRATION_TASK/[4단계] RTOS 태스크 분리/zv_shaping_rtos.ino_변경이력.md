## 절대 규칙

> **제어 수식, 명령어, 출력 내용을 바꾸지 않는다. 실행 구조만 바꾼다.**

계산식은 복사만 했다. 손으로 다시 쓰지 않았다.

검증은 두 가지로 했다.

**① 문자열 전수 대조** — 두 파일의 리터럴을 모두 뽑아 비교했다.

```
3단계 131종 137개  /  4단계 137종 143개
사라진 출력 : 0건
새 문자열   : "%s\n"(qprintln 내부)  "ctrl"  "io"  그리고 [rtos] 계측 줄 2개
```

**② 삭제된 코드 줄 전수 확인** — 들여쓰기·주석을 무시하고 원본에서 없어진 줄을
전부 뽑았더니 아래 6가지뿐이었고, **제어 수식 줄은 하나도 없었다.**

| 없어진 줄 | 수 | 왜 |
|---|---|---|
| `float GAIN = ...` 등 선언 | 17 | `volatile` 이 붙음 |
| `Serial.printf` / `println` | 13 | `qprintf` / `qprintln` 로 (내용 동일) |
| `arm` `stop` `t` `z` 처리 | 7 | 요청 큐로 |
| `float &d = ...` | 1 | `volatile float &d` |
| `zvRecalc(); zvClear();` | 4 | 잠금 추가 |
| `loop()` 머리 + 스트림 printf | 15 | `vTaskDelayUntil` + 스냅샷 큐 |

## 무엇이 바뀌었나

```
3단계                          4단계
loop() {                       ctrl (코어1, 우선순위6)   io (코어0, 우선순위2)
  handleSerial()                 vTaskDelayUntil(10ms)     큐에서 꺼내 출력
  10ms 지났나?                   요청 실행 (arm/stop/t/z)   handleLine()
  IMU→필터→ZV→제어→CAN           IMU→필터→ZV→제어→CAN
  로그 출력                      숫자만 큐에 ──────────────→
}                              loop() = vTaskDelay(1000)  껍데기
```

`ctrl` 본문의 순서는 3단계 `loop()` 와 같다.
`readIMU` → 상보필터 → 이상감지 → `drainCAN` → 합력벡터 → ZV → 제어 →
`sendBoth` → 출력 → 2초 상태.

`loop()` 를 지우지 않은 이유는 아두이노 `loopTask` 가 태스크 워치독에게 살아있다고
보고하는 역할을 겸하기 때문이다. 지우면 리셋이 걸릴 수 있어 껍데기로 남겼다.

### `dt` 가 가정에서 약속으로

`const float dt = 0.01;` 을 상보필터와 슬루(`MAX_RATE * dt`)가 쓴다.
3단계에는 그것을 보장하는 장치가 없었다 — 안 늦었을 뿐이다.
`vTaskDelayUntil` 은 OS 가 지킨다.

## 나누면서 생긴 위험 6가지 — 전부 막았다

**RTOS 자체의 문제가 아니다.** 일이 한 줄로 서 있으면 원리적으로 불가능했던 일들이
두 줄로 나누면 가능해진다. 그 "가능해진 것"이 위험이다.

```
3단계    A가 끝나야 B가 시작   →  둘이 부딪힐 수가 없다
4단계    A와 B가 진짜 동시에   →  부딪힐 수 있다
```

그래서 나누기 전에 여섯 곳을 막아야 했다. **여섯 개가 남아 있는 것이 아니라,
여섯 개를 찾아서 막았고 실기로 확인했다는 뜻이다.**

| # | 나누면 가능해지는 일 | 막은 장치 | 실기 확인 |
|---|---|---|---|
| ① | 두 태스크가 동시에 `Serial` 에 써서 줄이 섞인다 | 큐 2개, `io` 만 `Serial` 을 만진다 | 태스크 경합으로 인한 섞임 0건 |
| ② | `arm` 250ms 동안 제어 지령이 계속 나간다 | 명령 큐 + `ctrlBusy` | `arm` 중 지령 없음, `재동기 1` |
| ③ | ZV 계수 4개가 섞인 조합으로 읽힌다 | 스핀락 `zvMux` | `zd` 응답의 `A1/A2/A3` 가 3단계와 동일 |
| ④ | 시리얼 파서가 최대 1초 막혀 큐가 넘친다 | 문자 단위 비동기 파서 | `샘플드롭 0` |
| ⑤ | 밀린 틱을 간격 없이 몰아서 실행한다 | 매 틱 끝에서 재동기 | `10ms초과 0` |
| ⑥ | IDLE 태스크가 굶어 워치독이 리셋한다 | 반드시 기다리는 함수만 사용 | 26초 연속 구동 중 리셋 0 |

①②③④는 **코드 리뷰에서 지적받아 고친 것**이다. 처음 구현에는 `pendingCmd` 변수
유실, sweep 중 설정 변경, `zv1` 의 락 밖 대입, `readStringUntil` 블록이 실제로
남아 있었다. 아래에 각각 어떤 상태였고 어떻게 바꿨는지 적는다.

### ① 동시 출력 → 줄이 섞인다

**3단계에서는 불가능했다.** 출력하는 곳이 `loop()` 한 군데뿐이었다.

**안 막으면** 이렇게 된다.

```
정상 : t:123,pre_pitch:6.28,...,cmd_pitch:6.28
섞임 : t:123,pre_p!! 모터 이상itch:6.28,...
```

`check_tuning.py` 는 한 줄 안에서 `pre_pitch` 와 `cmd_pitch` 를 짝지어 읽는다.
줄이 깨지면 분석이 무너진다.

**막은 방법.** `Serial` 은 `io` 태스크만 만진다. `ctrl` 은 큐에 넣고 지나간다.
함수별로 전수 감사해 `ctrl` 쪽 출력 13곳을 `qprintf` / `qprintln` 으로 바꿨다.

```cpp
QueueHandle_t qEvt  = NULL;     // 텍스트 12통  — 모터이상·폭주차단·두절·DISARM 이유
QueueHandle_t qSnap = NULL;     // 샘플 32통   — 33Hz 스트림
```

**큐를 두 개로 나눈 이유가 따로 있다.** 하나로 두면 PC 가 멈춘 순간 샘플이 자리를
먼저 차지해서 **정작 원인이 되는 이벤트가 버려진다.** 제어는 돌아도 사후 분석이
막힌다. `io` 는 `qEvt` 를 먼저 비운다.

스트림은 **숫자만** 큐에 넣는다. `%.2f` 13개 포맷(수백 µs)은 `io` 가 진다.

`ctrl` 쪽 출력은 **대기 0** 이다. 처음에는 5ms 를 기다리게 했는데, PC 가 안 읽어서
큐가 차면 로그 한 줄마다 제어가 멈춘다 — 그걸 없애려고 나눈 것이라 앞뒤가 안 맞았다.
리뷰 지적으로 0 으로 바꿨다. 잃은 줄은 `dgEvtDrop` 으로 센다.

> **남은 것.** 태스크 경합은 없앴지만 USB 계층에서 0.45% 가 깨진다.
> 원인 미확정. [README 의 「아직 안 된 것」](README.md#usb-로그-줄-깨짐-045) 참고.

### ② `arm` 은 250ms, `t` 는 8초 블록한다  ← 제일 위험했다

```cpp
broadcastUniversal(0xFB);  delay(50);   // 에러 해제
broadcastUniversal(0xFE);  delay(50);   // 영점
sendBoth();                delay(50);
broadcastUniversal(0xFC);  delay(100);  // enable
```

**3단계에서는 이 250ms 동안 제어도 같이 멈춰 있었다.**

**안 막으면** — `io` 에서 실행하면 그동안 `ctrl` 이 CAN 지령을 계속 쏜다.
**영점을 재정의하는 중에 지령이 끼어든다.** 3단계에서는 물리적으로 불가능한
상황이고, 모터가 어디로 갈지 모른다. `motorsArm()` 은 I2C 도 쓰는데 `Wire` 는
두 태스크가 동시에 만지면 깨진다.

**막은 방법.** 요청 큐로 넘기고 `ctrl` 이 직접 실행한다. 같은 코드가 같은 것을
멈춘 채로 돌아서 3단계와 동작이 같아진다.

```cpp
QueueHandle_t qCmd = NULL;        // 명령 6통
volatile bool ctrlBusy = false;   // arm / t 실행 중
```

여기서 세부 세 가지를 리뷰에서 지적받아 고쳤다.

| 처음 구현 | 무엇이 잘못됐나 | 고친 것 |
|---|---|---|
| `volatile uint8_t pendingCmd` 변수 하나 | `ctrl` 이 읽고 지우는 사이에 들어온 명령이 사라지고, 연속 입력은 앞의 것을 덮어쓴다 | **큐** 로 바꿨다. `stop` 은 자리가 없으면 앞 명령을 하나 버려서라도 넣는다 |
| 명령 처리 뒤 공통으로 `ctrlBusy = false` | 큐에 `[z, arm]` 이 있으면 `z` 가 먼저 풀어버려 arm 250ms 동안 파서가 다시 열린다 | **`arm` 과 `t` 가 끝날 때만** 푼다 |
| `ctrlBusy = true; ctrlSend(1);` | 큐에 못 넣으면 풀어줄 사람이 없어 파서가 영영 멈춘다 | `ctrlSend` 를 `bool` 로 바꿔 **실패하면 되돌린다** |

**`ctrlBusy` 를 "차단" 이 아니라 "파서 정지" 로 한 이유.** 3단계는 sweep 8초 동안
`handleSerial()` 이 아예 안 불려서, 입력이 UART 버퍼에 쌓였다가 끝난 뒤 처리된다.
`ctrlBusy` 중 `Serial.read()` 를 하지 않으면 바이트가 그대로 남아 **동작이 정확히
같아진다.** 거부하거나 따로 보관하는 것보다 정확하다.

이걸 안 막으면 sweep 도중 `dr` 이 들어와 복귀 직후 roll 방향이 뒤집힌다.
출력 순서 문제가 아니라 모터가 달라지는 문제였다.

### ③ ZV 계수는 4개가 한 세트다

```cpp
void zvRecalc() {
  zv_n1 = ...;   // 반주기 [샘플]
  zv_A1 = ...;   // 임펄스 진폭
  zv_A2 = ...;
  zv_A3 = ...;
}
```

**안 막으면** `ctrl` 이 바꾸는 도중에 읽는다.

```
zv_A1 = 새 값,  zv_A2 = 옛 값   ← 섞인 조합
→ 그 틱만 엉뚱한 성형을 한다
```

`zvClear()` 는 링버퍼 float 256개를 지우므로 반만 지워진 것을 읽을 수도 있다.

**막은 방법.** 스핀락. `zvRecalc` · `zvClear` · `ctrl` 의 ZV 계산 블록 세 곳이다.

```cpp
portMUX_TYPE zvMux = portMUX_INITIALIZER_UNLOCKED;
```

**처음 구현에서 `zv1` 하나가 빠져 있었다.** 리뷰 지적으로 고쳤다.

```cpp
ZV_ON = ...;                                    // 락 밖 — 그 사이 한 틱이 지나간다
if (ZV_ON) { ZV_LOCK(); zvClear(); ZV_UNLOCK(); }
```

```cpp
bool zvOn = (s.substring(2).toInt() != 0);      // 변환은 락 밖에서 먼저
ZV_LOCK();
ZV_ON = zvOn;
if (zvOn) zvClear();
ZV_UNLOCK();
```

문자열 변환을 락 밖으로 뺀 것도 의도적이다. 임계구역 안에서 `String` 을 만들면
**인터럽트가 막힌 채로 힙을 건드린다.**

`zf` `zd` `zm` 은 처음부터 변경 전체를 잠갔다. 요청 큐 대신 락을 쓴 이유는 `zd` 가
계산 직후 `A1/A2/A3` 를 바로 찍기 때문이다 — 미루면 옛 값이 찍혀 출력이 달라진다.

**반면 홑겹 변수는 막을 필요가 없다.** `GAIN` `MOTOR_KP` `MAX_RATE` `ZV_ON`
`stream` 등은 32비트 단일 접근이 원자적이라 옛 값 아니면 새 값이지 섞인 값이
안 나온다. `volatile` 만 붙였다. `dp`/`dr` 의 `float &d` 는 `volatile float &d`
로 바꿔야 컴파일된다.

### ④ `readStringUntil` 은 최대 1초 막힌다

```cpp
String s = Serial.readStringUntil('\n');   // 개행이 안 오면 기본 1초 대기
```

**3단계에서는 이래도 됐다.** 막히면 전체가 같이 멈추니 잃는 것이 없었다.

**안 막으면** — `io` 가 그 1초 동안 큐를 못 비운다. **32칸 샘플 큐는 33Hz 에서
1초면 찬다.** 터미널이 `k` `p` `2` 를 나눠 보내기만 해도 로그가 통째로 날아간다.

**막은 방법.** 문자 단위 비동기 파서. `handleSerial()` 을 `handleLine(const char*)`
로 바꿨고, 명령·응답 내용은 그대로다.

```cpp
while (!ctrlBusy && Serial.available()) {
  char c = Serial.read();
  if (c == '\n' || c == '\r') { if (n) { line[n] = 0; n = 0; handleLine(line); } }
  else if (n < sizeof(line) - 1) line[n++] = c;
}
```

`'\r'` 도 종결로 본다. 3단계는 `readStringUntil('\n')` 뒤에 `trim()` 을 했으니
결과가 같다.

### ⑤ 밀린 틱을 몰아서 실행한다

**처음 구현은 `arm`/`t` 뒤에만 시계를 맞췄다.** 리뷰에서 이것으로 부족하다는
지적을 받았다.

`configSensor()` 는 **명령이 아니라 센서 이상 감지에서 자동으로 불리고**, 정상
실행만으로 150ms 를 쓴다.

```cpp
writeReg(REG_CTRL3_C, 0x01);  delay(50);    // 소프트 리셋
...                           delay(100);
```

I2C 가 응답 없으면 여기에 최대 50ms 가 더 붙는다.

**안 막으면** `vTaskDelayUntil` 이 밀린 틱을 **10ms 간격 없이 연속으로 따라잡는다.**
제어 계산과 CAN 전송이 한꺼번에 몰린다.

**막은 방법.** 특정 명령 뒤가 아니라 **매 틱 끝에서** 실제 지연을 검사한다.

```cpp
if ((TickType_t)(xTaskGetTickCount() - xLastWake) >= pdMS_TO_TICKS(20)) {
  xLastWake = xTaskGetTickCount();
  dgResync = dgResync + 1;
}
```

계측 시작점도 명령 처리 **뒤**로 옮겼다. `arm` 의 의도된 250ms 정지를 같이 세면
(실측 270,621 µs 로 찍혔다) 정작 제어 틱이 늦었는지를 볼 수 없다.

### ⑥ 바쁜 대기는 워치독 리셋을 부른다

FreeRTOS 워치독은 어떤 태스크가 CPU 를 놓지 않으면 죽은 것으로 보고 **보드를
리셋한다.** 3단계에는 태스크가 하나였으니 해당이 없었다.

```cpp
while (!Serial.available()) { }     // ← 이렇게 짜면 리셋된다
```

**막은 방법.** 둘 다 반드시 기다리는 함수를 쓴다.

- `ctrl` → `vTaskDelayUntil(&xLastWake, pdMS_TO_TICKS(10))`
- `io`   → `xQueueReceive(qSnap, &sn, pdMS_TO_TICKS(5))`

아두이노 `loopTask` 도 지우지 않고 `vTaskDelay(1000)` 껍데기로 남겼다. 이 태스크가
워치독에게 살아있다고 보고하는 역할을 겸한다.

## 실측값을 기본값으로

3단계 기본값은 매번 손으로 넣어야 해서 빠뜨리는 사고를 두 번 겪었다.
시리얼 명령으로 여전히 바꿀 수 있다.

| 항목 | 3단계 | 4단계 | 근거 |
|---|---|---|---|
| `MAX_RATE` | 30 | **120** | 요구 변화율 p95 가 101~112 °/s. 30 이면 지령의 31% 가 잘려 ZV 성형이 무너진다 |
| `MOTOR_KP` | 1.0 | **2.0** | 드룹 54~82% → 89% |
| `MOTOR_KD` | 0.13 | **0.13** | `Kd ∝ √(Kp+k)`, `k ≈ 0.28 N·m/rad` |

`k` 는 트레이 무게중심이 축보다 아래에 있어 생기는 복원 강성이다.
정지 구간에서 `act/cmd` 가 일정 비율로 모자란 것(오프셋 −0.38°/+0.10°, 거의 0)에서
`k = Kp·(1/droop − 1)` 로 냈다. 마찰이면 비율이 아니라 고정 오프셋으로 나타난다.

### ZV 성형은 슬루를 더 걸지 않는다

같은 로그에서 ZV 만 뺀 반사실 계산을 돌렸다 (`ref_*` 와 `zv_*` 가 둘 다 기록돼 있다).

| | ZV 끔 | ZV 켬 |
|---|---|---|
| pitch 슬루 걸림 | 10.8% | 10.9% |
| roll 슬루 걸림 | 12.3% | **10.0%** |
| roll 요구 p95 | 133 °/s | **122 °/s** |

임펄스 합이 1이고 둘 다 양수라 **가중 이동평균**이다. 계단이 하나 늘지만 각 계단
높이가 절반이라 최대 변화율은 오히려 내려간다.
(절대값은 33Hz 로그를 100Hz 로 재구성한 탓에 부풀려져 있다. 차이만 유효하다.)

## CAN 송신 대기 0

```cpp
if (twai_transmit(&m, 0) != ESP_OK) dgTxFail = dgTxFail + 1;   // sendMIT
```

`sendMIT` 은 50Hz 로 계속 나가는 주기 지령이라 한 장 버려도 20ms 뒤 다음 장이 간다.
반면 5ms 를 기다리면 두 축이 10ms — **한 틱 예산 전부**다.

**실측 근거.** 모터 전원을 끈 채 `arm` 하면 CAN ACK 가 없어 송신 큐가 막힌다.

| | 5ms 대기 | 대기 0 |
|---|---|---|
| `10ms초과` | **17** | **1** |
| `TX실패` | 36 | 36 |

실패 **횟수**는 같고 **대기 시간**만 사라진다 (송신 큐 5칸이 차면 그 뒤는 어차피 실패).
정상 CAN 에서는 큐가 안 차므로 `TX실패 0` 이고 동작이 같다.

남은 1건은 `motorsDisarm` 의 `broadcastUniversal(0xFD)` 다. `sendUniversal` 은
비주기 명령이라 **한 장이 중요해서 5ms 를 그대로 뒀다.** 2축 × 5ms + 1ms = 11.0ms 이고
실측 11,023 µs 와 맞는다. CAN 이 이미 죽었을 때 정지하는 순간 한 번이라 그대로 둔다.

## 실기 검산

`RTOS_DIAG` 계측을 넣고 실기에서 확인했다.
`t:` 간격만으로는 100Hz 누락을 못 잡는다 — 출력 게이트가 틱 안에 있어서
**틱 하나가 빠져도 앞뒤 출력이 30ms 로 보인다.** 그래서 틱 자체를 쟀다.

### 모터 전원 OFF, arm 안 함

```
최대틱 490~630us   10ms초과 0   재동기 0   TX실패 0   드롭 전부 0
```

### 모터 전원 ON, `arm`, 26초 캡처

```
최대틱 550~593us   10ms초과 0   재동기 1   TX실패 0   드롭 전부 0
피드백 2523회 (100/s = 50Hz × 2축)
```

`재동기 1` 은 `arm` 의 `delay` 250ms 때 한 번이다. 설계대로다.
계측 시작점을 명령 처리 **뒤**로 두었다. `arm` 의 의도된 정지를 같이 세면
(실측 270ms 로 찍혔다) 제어 틱이 늦었는지를 볼 수 없다.

### 3단계 로그와 비교

같은 도구(`capture.py` → `check_tuning.py`)로 같은 조건에서 비교했다.

| | 3단계 | 4단계 |
|---|---|---|
| pitch 드룹 | 89% | **89%** |
| pitch 추종오차 RMS | 3.31° | 3.18° |
| pitch 슬루 걸림 | 6% | 4% |
| roll 슬루 걸림 | 7% | 6% |
| pitch 요구 p95 | 101 °/s | 96 °/s |

**드룹이 정확히 같다.** 나머지 차이는 흔든 세기 차이다 (요구 변화율이 전반적으로
낮다 = 덜 세게 흔들었다). roll 드룹과 떨림은 계속 흔들어 정지 구간이 없어서
안 나왔다 — 다음에는 흔들다가 2초쯤 멈추기를 서너 번 섞어야 한다.

### 피드백 두절 워치독

`b41de99` · 2026-09-01 10:04 푸시

> ⚠ **위의 절대 규칙("명령어·출력을 바꾸지 않는다")을 깬 변경이다.**
> 사용자 요청으로 넣었다. 명령 4개와 상태 출력 1줄이 늘었다.
> 제어 수식은 건드리지 않았다.

### 왜 필요했나

지령→실제 지연을 상호상관으로 쟀더니 두 축이 크게 달랐다. 두 번의 캡처에서
같은 값이 나왔다.

| 축 | 최적 지연 | 그때 상관 | 지연 0 에서 상관 |
|---|---|---|---|
| 안쪽 (PITCH, `0x02`) | **108 ms** | +0.961 | +0.681 |
| 바깥 (ROLL, `0x01`) | **189 ms** | +0.925 | **+0.192** |

지연을 보정하면 둘 다 지령을 잘 따라간다. **부호도 배선도 정상이고 바깥축이
느릴 뿐이다.** 다만 지연 0 에서의 상관이 +0.19 라, 지금 이 순간의 트레이
자세가 지금 필요한 자세와 거의 무관하다. 눈으로 보면 엉뚱하게 도는 것처럼
보이는 이유다.

189 ms 는 슬로싱 주기 420 ms 의 **45%**, 위상으로 162° 다. 거의 역위상이라
직전 반주기에 대한 보정이 지금 나타난다. 액체를 올리면 이 축은 슬로싱을
억제하지 않고 키운다.

힘이 모자란 것이 아니다. 추종률 **0.94** 로 크기는 충분히 간다. 대역폭이
문제고, 원인은 바깥축이 안쪽 짐벌과 트레이를 통째로 이고 있어 관성이 크기
때문이다. `ω ≈ √(Kp / J)` 이므로 하나의 `Kp` 로 두 축을 맞출 수 없다.

### 명령

| 명령 | 대상 | 예 |
|---|---|---|
| `kp<값>` `kd<값>` | 두 축 함께 (기존과 동일) | `kp2.0` |
| `kpp` `kdp` | 안쪽 `0x02` | `kpp2.0` |
| `kpr` `kdr` | 바깥 `0x01` | `kpr6` |

> ⚠ `kpp`/`kpr` 은 `kp` 보다 **먼저** 검사해야 한다. 순서가 뒤바뀌면
> `kpr6` 이 `kp` 접두에 걸려 `substring(2)` = `"r6"` → `toFloat()` = **0** 이
> 된다. 게인이 0 으로 조용히 들어가 모터가 풀린다.
> `ag` 를 `g` 보다 먼저 보는 것과 같은 함정이다.

게인을 바꾸면 항상 두 축을 나란히 찍는다. 한쪽만 올리고 다른 쪽을 잊는 것이
이 구조에서 가장 하기 쉬운 실수라서다. `Kp` 만 올리고 `Kd` 를 안 올리면
경고도 띄운다 — 바깥축은 1.75Hz 한계진동 이력이 있다.

### 기본값은 그대로 두었다

```cpp
KP_PITCH 2.0   KD_PITCH 0.13
KP_ROLL  2.0   KD_ROLL  0.13     // 올려야 할 쪽
```

189 → 108 ms 로 줄이려면 `ω` 를 1.75배, 즉 `Kp` 를 3배(2.0 → 6.0) 로 올려야
한다. 그러면 `ζ = Kd / 2√(Kp·J)` 가 √3 배 떨어지므로 `Kd` 도 1.7배
(0.13 → 0.22) 를 같이 올린다.

계산값은 출발점일 뿐이고, 발진 이력이 있는 축이라 컴파일에 박지 않았다.
`kpr`/`kdr` 로 올려가며 **지연을 다시 재서** 확정할 것.

### 아직 안 끝났다

`kpr4` `kdr0.22` 로 올린 상태에서도 바깥축이 반대로 도는 것으로 관측됐다.
`Kp` 2→4 는 `ω` 가 √2배라 지연이 189 → 약 134 ms, 위상 115° 로 예상된다.
나아지지만 여전히 늦다.

남은 판단.

| 항목 | 값 | 성격 |
|---|---|---|
| `CMD_LPF` 0.15 | τ ≈ 67 ms | **두 축 공통.** `Kp` 로는 이 아래로 못 내려간다 |
| ZV 성형 | +102 ms | 켜면 바깥축이 290 ms = 주기의 69% 가 된다 |

**바깥축 지연을 잡기 전에는 ZV 를 켜면 안 된다.**

부호 오류인지 지연인지는 **아주 느린 가속**으로 가른다. 느리면 지연이 문제가
안 되므로, 그때도 반대로 기울면 진짜 부호 오류이고 `DIR_ACC` 를 축별로 나눠야
한다. 툭툭 미는 동작으로는 둘을 구분할 수 없다.

## 회전시키면 부호가 뒤집힌다

roll 축이 슬로싱을 키우는 쪽으로 기운다고 관측됐던 건이 여기서 풀렸다.
**평행이동이 아니라 로봇 뒷부분만 밀어 회전시키고 있었다.** 좌우로 평행이동
시키면 pitch 와 똑같이 올바른 방향으로 기운다.

### 왜 그런가

제어는 이 전제 위에 있다.

```
IMU 가 느끼는 가속도  =  트레이(액체)가 느끼는 가속도
```

평행이동이면 강체의 모든 점이 같은 가속도를 받으니 성립한다. **회전이면
성립하지 않는다.**

```
a(점) = a_중심 + α × r + ω × (ω × r)
```

회전 중심에서 거리가 다르면 가속도가 다르고, **IMU 와 트레이가 회전 중심의
반대쪽에 있으면 부호까지 반대**가 된다. 뒷부분만 밀었을 때 IMU 는 크게
휘둘렸지만 트레이는 덜 움직였거나 반대로 움직였다.

### 시험 방법 문제가 아니다

**바퀴 로봇이 코너를 돌면 정확히 이 상황이다.** 제자리 선회든 곡선 주행이든
회전이 섞이고, 그때마다 IMU 와 트레이의 가속도가 달라진다.

### 고칠 재료는 이미 있다

```cpp
readIMU(ax, ay, az, gx, gy, gz);
//                          ^^ 읽기만 하고 쓰지 않는다
```

`gz`(요 각속도)로 지렛대 보정이 가능하다.

| 필요한 것 | 상태 |
|---|---|
| `gz` | 이미 읽고 있다 |
| `gz` 미분 (각가속도 α) | 계산 가능 |
| **IMU→트레이 거리 벡터 `r`** | **차체 완성 후 실측** |

차체가 확정되고 `r` 이 정해지면 넣는다. 지금 순서로는 지연 단축이 먼저다.

|---|---|

정사각형이라 두 축의 슬로싱 주파수가 같다. `zf` 하나로 두 축을 덮는다.

기존 설정 2.40 Hz 는 **9.4% 높다.** 천수 근사 `√(gh)/2L = 2.42 Hz` 와 거의
같은데, `h/L = 0.26` 은 천수 영역이 아니라 `tanh` 를 살려야 한다.

### `act` 로 재려던 시도는 실패했다

모터를 켜두면 출렁이는 물이 트레이를 밀고, 그 흔들림이 `act` 에 잡힐 것이라
보고 `kp1.0` 으로 낮춰 캡처했다. **틀린 설계였다.**

- 용기가 트레이 위에 있어 **손으로 친 것과 물이 민 것을 구분할 수 없다**
- `Kp 1.0` 에서 트레이 자체 공진이 **0.8 Hz** 다. 슬로싱 2.2 Hz 보다 **아래**라
  트레이가 2.2 Hz 를 감지할 수 있는 조건이 아니었다

스펙트럼도 0.8 Hz 와 그 2배인 1.6 Hz 가 지배했고 2.2 Hz 에는 거의 없었다.
`Kp` 를 낮추면 민감해질 것이라 본 것부터 반대였다.

### 제대로 재려면 로봇을 쓰지 않는다

슬로싱 주파수는 용기와 물 높이만으로 정해진다. 짐벌도 모터도 무관하다.

```
1. 용기를 단단한 책상에 올린다
2. 10~15° 기울였다 놓는다
3. 옆에서 촬영 (슬로우모션이면 더 좋다)
4. f = 왕복 횟수 / 걸린 시간
5. 진폭이 절반 되는 데 n 주기 →  ζ ≈ 0.11 / n
```

`ζ` 는 계산으로 안 나온다. 오직 실측이다.

## 가속 종료 소프트 복귀

`e054139` · 2026-09-03 23:01 푸시

`지연_개선_실험/soft_return_rtos.ino` 에서 제어 부분만 옮겼다. 그 파일에 있던
속도 피드포워드(`v_des`)와 CAN 진단은 **가져오지 않았다.**

### 무엇을 해결하려는가

직접보상 목표각은 **현재** 가속도만 본다. 그래서 가속이 끝나면 `θ_ref` 가
곧바로 0 으로 사라지고 트레이가 급히 수평으로 돌아온다. 그런데 액체는 과거
가속의 상태를 아직 갖고 있어서, 그 급정지가 **새 슬로싱을 만든다.**

가속 종료 시점에 남아 있는 목표각을 잠시 유지한 뒤 최소저크 곡선으로 0 까지
보낸다. **시작 구간은 건드리지 않으므로** 직접보상의 빠른 반응은 그대로다.

### 상태 기계 — 축마다 독립

```
DIRECT  →  HOLD  →  RETURN  →  LEVEL
```

| 상태 | 하는 일 |
|---|---|
| `DIRECT` | `ref` 를 그대로 통과. 평소 동작 |
| `HOLD` | 종료 시점의 `ref` 를 `SR_HOLD_MS` 동안 유지 |
| `RETURN` | `SR_RETURN_MS` 동안 최소저크로 0 까지 |
| `LEVEL` | 통과. 새 가속이 오면 `DIRECT` 로 |

종료 판정은 **`ACC_LPF` 를 걸기 전의 `raw_ref`** 로 한다. 필터를 통과한 값은
가속이 끝나도 꼬리가 남아 판정이 늦다.

```cpp
if (a <= SR_END_DEG) {
  if (++s.quietTicks >= dwellTicks) {
    s.holdAngle = ref;       // 현재 출력과 같아 진입 시 불연속이 없다
```

`holdAngle` 을 `ref`(필터 통과값)로 잡는 것이 요점이다. 판정은 `raw_ref` 로
빠르게 하고, 유지할 값은 지금 실제로 나가고 있는 값을 쓴다. 그래서 상태가
바뀌는 순간 목표각에 계단이 생기지 않는다.

최소저크 곡선은 5차 다항식이다.

```cpp
float smooth = x * x * x * (10.0f + x * (-15.0f + 6.0f * x));
float out = s.holdAngle * (1.0f - smooth);
```

시작과 끝에서 속도·가속도가 모두 0 이라 복귀 자체가 슬로싱을 새로 만들지
않는다. 선형 램프는 양끝에서 가속도가 튄다.

### 새 가속이 꼬리보다 우선한다

```cpp
if (s.phase != SR_DIRECT && a >= SR_ACTIVE_DEG) {
  softReturnResetAxis(s);
  s.sawActive = true;
  return ref;
}
```

`HOLD`/`RETURN` 중에 새 가속이 들어오면 즉시 `DIRECT` 로 돌아간다. 꼬리를
지키느라 실제 가속을 놓치면 본래 목적에 어긋난다. 전환 계단은 `CMD_LPF` 와
슬루가 제한한다.

### ZV 와 동시에 쓰지 않는다

목적이 겹친다. 둘 다 목표각을 성형해 슬로싱을 줄이는 것이라 겹쳐 쓰면
서로의 타이밍을 무너뜨린다. `sr1` 이 `ZV_ON` 을 끄고, `zv1` 이
`SOFT_RETURN_ON` 을 끈다.

```cpp
if (SOFT_RETURN_ON)      shaped = softReturnStep(...)
else if (ZV_ON)          shaped = ZV 성형
else                     shaped = ref
```

### 명령

| 명령 | 기본 | 뜻 |
|---|---|---|
| `sr1` / `sr0` | **꺼짐** | 켜기 / 끄기 (켜면 ZV 자동 꺼짐) |
| `sra<값>` | 1.50° | 이 이상을 실제 가속으로 인정 |
| `sre<값>` | 0.75° | 이 아래가 지속되면 종료 |
| `srd<값>` | 30 ms | 종료 확인 시간 |
| `srh<값>` | 100 ms | 남은 목표각 유지 시간 |
| `srr<값>` | 120 ms | 최소저크 복귀 시간 |

> ⚠ `sra`/`sre`/`srd`/`srh`/`srr` 은 `sr` 보다 **먼저** 검사해야 한다.
> 순서가 뒤바뀌면 `sra2` 가 `sr` 접두에 걸려 `substring(2)="a2"` →
> `toInt()=0` 으로 소프트복귀가 조용히 꺼진다. `ag`/`g`, `kpr`/`kp` 와 같은
> 함정이다.

`sra > sre` 를 명령 단계에서 검사한다. 뒤집히면 종료 판정이 성립하지 않는다.

### 상태는 ctrlTask 만 만진다

```cpp
if (srResetRequest || !SOFT_RETURN_ON) {
  softReturnReset();
  srResetRequest = false;
}
```

`ioTask` 는 설정값만 바꾸고 `srResetRequest` 를 세운다. 축 상태(`phase`,
`quietTicks`, `holdAngle`)는 `ctrlTask` 하나만 초기화·갱신한다. 두 태스크가
같은 상태 기계를 만지면 전환 도중의 조합이 나온다.

`arm`/`disarm` 에서도 초기화한다. 기울어진 채 남은 `holdAngle` 이 다음 arm
때 되살아나지 않게 한다.

### 아직 실측 전이다

기본값 `100ms 유지 / 120ms 복귀` 는 팀원분이 정한 출발점이고, 물을 올린
상태에서 확인한 값이 아니다. 슬로싱 주기(11×11 용기, 350mL 에서 456ms)와의
관계를 재봐야 한다.

`1fc56cc` 까지는 `?` 를 쳐도 ZV 와 소프트복귀가 켜져 있는지 알 수 없었다.
ZV 는 처음부터 `printStatus` 에 없었고, 소프트복귀 줄은 넣었다고 적었는데
치환이 조용히 실패해 실제로는 안 들어가 있었다.

```
       ZV OFF   2.40Hz  z=0.020  2임펄스  지연 +102ms
       소프트복귀 ON    sra 1.50°  sre 0.75°
```

## 합력각 직접 방식으로 바꿨다

`37f9c0e` · 2026-09-03 23:33 푸시

팀원분의 `zv_shaping_rtos__direct_force_sr_v2.ino` 에서 제어 개선 네 가지만
가져왔다. 기본값 변경과 속도 피드포워드는 **가져오지 않았다.**

### 1. θ_ref — 중력 제거 대신 합력각을 직접 쓴다

```cpp
// 전 : 중력을 빼서 선형가속을 복원한 뒤 각도로
p_lin     = ay - one_g * sin(θ_base);
raw_ref_p = -atan2(p_lin, one_g);

// 후 : 합력 벡터의 방향을 그대로
force_pitch = atan2(force_ay, √(force_ax² + force_az²));
ref_pitch   = θ_base - force_pitch;
```

두 방식 다 최종 지령에서 `θ_base` 가 소거된다.

```
want = ACC_GAIN·ref − GAIN·θ_base = −θ_force      (GAIN = ACC_GAIN 일 때)
```

차이는 정확도다. 예전 방식은 `one_g` 를 **상수**로 썼는데, 가속 중에는 비력의
크기가 `g` 가 아니다. 그래서 경사면에서 가속할 때 오차가 남았다.

| 차체 기울기 | 가속 | 정답 | 새 방식 | 예전 방식 |
|---|---|---|---|---|
| 0° | 0.3g | −16.70° | −16.70° | −16.70° |
| 20° | 0.3g | −16.70° | −16.70° | **−15.74°** |
| 30° | 0.3g | −16.70° | −16.70° | **−14.56°** |

30° 에서 2.1° 덜 기운다. 합력각 방식은 벡터의 **방향만** 보므로 모든 각도에서
정확하고 `g_scale` 오차에도 영향을 받지 않는다.

### 2. 각도가 아니라 벡터를 거른다

```cpp
force_ax = ACC_LPF * ax + (1 - ACC_LPF) * force_ax;   // 성분 상태에서
... 3축 모두 ...
force_pitch = atan2f(force_ay, ...);                  // 그 뒤 한 번만 각도로
```

축별로 각도를 따로 거르면 두 축이 동시에 움직일 때 벡터의 길이와 방향이 서로
어긋난다. `ACC_LPF` 의 의미가 "목표각 필터" 에서 "3축 벡터 필터" 로 바뀌었다.
기본값 0.20 은 그대로 두었다 — 1차 필터라 시간상수가 같다.

### 3. SR 에 CONFIRM 단계 — 붙잡는 각도가 안 깎인다

```cpp
// 전 : dwell 이 끝난 뒤에 잡는다
if (s.quietTicks >= dwellTicks) { s.holdAngle = ref; }

// 후 : 문턱을 넘는 순간 직전 값을 잡고, 확인은 CONFIRM 에서
s.holdAngle = s.lastActiveAngle;
s.phase = SR_CONFIRM;
```

예전 방식은 30ms 의 dwell 동안 `ACC_LPF` 가 이미 목표각을 0 쪽으로 깎아놓아
**HOLD 가 실제 피크보다 약했다.** 문턱을 넘기 직전 값을 따로 들고 있다가
(`lastActiveAngle`) 그것을 붙잡는다.

`CONFIRM` 중에 가속이 다시 올라오면 `DIRECT` 로 되돌아간다. 오판을 물릴 수
있게 됐다.

```
DIRECT → CONFIRM → HOLD → RETURN → LEVEL
            ↑ 여기서 되돌아갈 수 있다
```

### 4. 자세 보정 게이트

자이로 예측과 가속도계 각이 `SR_ACTIVE_DEG` 이상 벌어지면 그 축은 자이로
예측만 쓴다. 상보필터가 수평가속을 기울기로 학습하는 것(경사/가속 모호성)을
막는다.

> ⚠ **이 게이트는 모터 지령을 바꾸지 않는다.** `want = ref − θ_base` 에서
> `ref = θ_base − θ_force` 이므로 `θ_base` 가 소거되기 때문이다.
> 게이트가 있든 없든 지령은 `−θ_force` 다.
>
> 바뀌는 것은 두 가지다.
>
>   1. 로그의 `pitch` / `ref` 값이 정직해진다
>   2. **SR 의 종료 판정이 정직해진다** ← 실질적 이득
>
> 게이트가 없으면 가속 중 `θ_base` 가 가속을 흡수해 `raw_ref` 가 씻겨나가고,
> SR 이 "가속이 끝났다" 고 조기 오판한다.

`?` 에 `자세보정게이트 TRACK/BLOCK` 으로 현재 상태가 나온다.

### 가져오지 않은 것

| 항목 | v2 | 여기 | 이유 |
|---|---|---|---|
| `MAX_RATE` | 60 | **120 유지** | `결과_분석.md` 가 요구 변화율 p95 를 109~112 로 측정했다. 60 이면 절반이 잘린다 |
| `SOFT_RETURN_ON` | true | **false 유지** | 올려도 동작이 안 바뀌어야 한다는 규칙 |
| `KP_PITCH`/`KD_PITCH` | 4.0/0.20 | **2.0/0.13 유지** | 실험이 채택한 값은 2.0/0.13 이다 |
| `CMD_LPF` | 0.30 | **0.15 유지** | 실험은 0.30 을 지지하지만 이번 변경과 섞지 않는다 |
| 속도 피드포워드 | 있음 | **없음** | 앞서 제거하기로 한 건 |

### ZV 와의 관계 — 아직 정리 안 됨

시뮬레이션상 2.19Hz 를 안 깨우려면 어떤 방법이든 한 주기(456ms)에 걸쳐
움직여야 한다. ZV 는 그 구조가 주기에서 유도되지만, SR 의 세 시간
(30+100+120 = 250ms)은 슬로싱 주기와 무관하게 정해진 값이다.

그리고 **SR 은 종료 구간만 손댄다.** 가속이 시작될 때의 급변은 그대로다.
ZV 는 양쪽을 모두 성형한다.

지금 코드는 둘을 상호배타로 묶어놓았는데, 역할이 겹친다기보다 SR 이 ZV 의
부분집합에 가깝다. 주파수를 실측한 뒤 다시 볼 문제다.

두 변경 다 예측한 자리에서 예측한 만큼 빠졌고 상관 0.99 이상으로 안정성 손상은 없다.
슬루는 `r120` 에서 클리핑 0% — 병목이 아니다.

### `kpp6 kdp0.25` 는 두 번 다 실패했다

한 번은 arm 3초 만에 CAN 피드백 두절(`TX실패 58`), 한 번은 arm 도 못 갔다. 그 뒤
직접 돌려본 결과는 **모터가 뚝뚝 끊기고 액체가 요동**. `Kd` 는 엔코더 속도 잡음을,
`Kp` 는 IMU 잡음 한 눈금을 그대로 토크 계단으로 만든다. 그 고주파 떨림이 물의
2·3차 모드(3.6/4.6Hz)를 직접 친다. CAN 이 죽은 것도 토크 스파이크 → 24V 처짐으로
보인다.

**모터 구간 60ms 가 이 하드웨어의 바닥이다.** 지연을 강성으로 더 줄이는 길은
닫혔고, 총지연 85ms(ZV 제외) 위에서 설계해야 한다. 매끄러움이 지연만큼 중요하다는
것도 여기서 확인됐다.

### 슬로싱 실측 2.0 Hz

`g0 ag0 zv0 arm` 으로 트레이를 고정 용기처럼 붙잡고 카트를 밀어 수면을 셌다.
**1초에 2회 왕복, 주기 500ms.** 책상 계산값 2.19Hz 보다 9% 낮은데, 짐벌이
완전 강체가 아니라 결합계 주파수가 내려간 것으로 본다.

### `zf` 는 아직 2.40 이다

실측 2.0 과 20% 어긋나지만 그대로 두었다. 두 목표가 충돌하기 때문이다.

| `zf` | ZV 자체 상쇄 | 밀기 슬로싱 반대위상 (지연 85ms 포함) |
|---|---|---|
| 2.40 | 80% | **86%** |
| 2.00 | **99%** | 48% |

두 번째 임펄스가 물에 닿는 시각은 `85ms(지연) + 간격` 인데, 밀기가 만든 슬로싱의
반대 위상은 250ms 다. `zf2.4` 의 간격 208ms 가 우연히 그 근처(293ms)에 앉아 있어
"반대 위상 한 방에 잡히는" 것이 보인다. `zf2.0` 이면 335ms 로 밀려 절반으로 약해진다.

지연이 0 이면 두 최적이 250ms 로 일치한다. 지연이 85ms 로 고정된 지금은 절충점을
눈으로 A/B 해서 정한다. 결과가 나오면 여기 적는다.

## 각도 상한을 기구 한계까지

`0d9216a` · 2026-09-04 02:29 푸시

```
ACC_REF_LIMIT   20° → 45°     합력 목표각 상한  (0.36g → 1.0g)
LIMIT_DEG       25° → 45°     지령 상한
ACT_LIMIT_DEG   50° → 55°     폭주 차단 (지령 상한 +10°)
```

### 세게 밀어도 트레이가 더 안 기울던 이유

세 캡처 모두 `raw_pitch` 최대가 **정확히 20.0°** 였다. `ACC_REF_LIMIT` 에 잘린
것이다. 보통 리듬으로 밀 때도 1.4~2.6% 가 상한에 붙어 있었고, 세게 밀면
그 비율만 올라갈 뿐 트레이는 20° 에서 멈춘다. 20° 는 0.36g 다.

그 위에 사슬 손실이 곱해진다 — ACC_LPF 0.75, ZV 0.83, 모터 0.95 — 그래서
실제 `act` 는 9~12° 에서 끝났다. 짧고 센 밀기일수록 필터가 더 깎는다.

`want` 의 25° 상한과 슬루(`r120`)는 안 걸렸다.

기구 한계가 45° 로 확인돼 세 값을 거기 맞췄다. 폭주 차단은 지령 상한 바로
위에 두면 정상 동작이 차단에 걸리므로 10° 여유를 둔다.

> 목표가 커지면 요구 변화율도 커진다. 전에 17° 목표에서 155°/s 가 나왔으니
> 40° 목표면 `r120` 이 잘라낼 수 있다. `pre` 와 `cmd` 의 차이로 확인할 것.

### 위상 문제는 센서 없이는 우연이다 — 받아들이기로 했다

밀기가 이미 만든 출렁임을 트레이가 반대 위상으로 잡는 것은 **가끔** 된다.
트레이의 타이밍은 밀기 시작 시점에 고정(지연 85ms + ZV 간격)돼 있고 액체의
위상은 밀기의 길이·모양에 따라 매번 다르기 때문이다. 겹치면 거의 안 흔들리고,
어긋나면 오히려 키운다. 우연의 분포다.

이걸 우연이 아니게 만들려면 액체의 위상을 아는 신호가 필요하다.

| 방법 | 결론 |
|---|---|
| 트레이 IMU 를 루프에 | 시도해봤으나 **물이 너무 가벼워 IMU 가 액체 상태를 못 읽는다** |
| 별도 액체 센서 | 지금 살 수 없다 |
| 차체 IMU 에서 반작용력 대역통과 | 트레이 IMU 도 못 읽는 힘이 차체까지 올 가능성은 낮다 |

**차체 IMU 만으로 하는 개루프의 한계로 받아들인다.** ZV 가 보장하는 것은
트레이 자신의 움직임이 출렁임을 만들지 않는 것까지이고, 밀기가 만든 출렁임에
대한 위상은 보장하지 않는다.

이 결정의 함의 하나 — `zf` 는 실측값 2.0 이 맞다. 2.4 가 좋아 보였던 것은
반대 위상 우연이 잘 맞은 경우였는데, 그 우연을 포기하기로 했으니 남는 것은
ZV 가 **보장하는** 자체 상쇄이고, 그것은 `zf` 가 정확할 때 최대다.

## `zf` 를 실측값 2.00 으로
