## ⚠ 설계안에서 바꾼 것 — 태스크를 5개가 아니라 2개로

앞선 4단계 제안은 `ctrl` / `can_tx` / `can_rx` / `io` / `safety` 5개였다.
**2개만 만들었다.** 이유는 셋이다.

### ① 제안이 짚은 핵심이 2개로 달성된다

> 핵심은 `io` 를 코어 0 의 낮은 우선순위로 빼는 것이다.

그대로 했다. `io` 가 아무리 막혀도 코어 1 의 `ctrl` 은 영향을 안 받는다.

### ② 남은 셋은 쪼갤 근거가 측정으로 사라졌다

한 틱이 **550 µs** 다. 10 ms 예산의 5.6 % 다.

| 제안 태스크 | 왜 안 만들었나 |
|---|---|
| `can_tx` | 송신은 틱 안에서 끝난다. 정상 CAN 에서 **TX실패 0**. 따로 뺄 이유가 없다 |
| `can_rx` | 피드백이 **초당 100회** (50Hz × 2축) 로 오고 100Hz 폴링이 그것과 같은 주기다. 유실 0 |
| `safety` | 판정 대상이 `act_deg` 와 `lastFb` 뿐이다. 별 태스크로 빼면 **읽는 시점이 제어와 어긋나** 오히려 늦게 잡는다 |

### ③ 태스크를 늘리면 공유 상태 위험이 제곱으로 늘어난다

제안서가 지적한 ZV 계수 문제가 정확히 그것이다. 태스크 2개에서도
**락 1개, 큐 3개, 요청 플래그 1개**가 필요했다. 5개면 여기에
`act_deg` · `armed` · `cmd_pitch/roll` · `lastFb` 가 전부 경합 대상이 된다.

**측정된 이득이 없는데 검증 못 할 위험을 늘리지 않는다.** 지금 구조는
"제어식이 안 바뀌었다"를 문자열 전수 대조와 로그 비교로 증명할 수 있다.

필요해지면 `can_rx` 부터 추가하면 된다. 락과 큐가 이미 그 자리에 있다.

## 정정 — 시리얼 61% 계산은 성립하지 않는다

제안서의 근거는 이랬다.

```
스트림 한 줄 140자 → 115200 8N1 에서 12.3 ms → 20ms 주기의 61%
```

**ESP32-S3 는 네이티브 USB CDC 라 baud 가 무의미하다.** `Serial.begin(115200)` 의
숫자는 무시되고 실제로는 USB Full-Speed(12 Mbps) 로 나간다. 170자 한 줄이
12.3 ms 가 아니라 수십 µs 다.

실측이 그것을 확인한다. 스트림을 33Hz 로 흘리는 중 **최대 틱 550 µs** 였다.
한 줄에 12.3 ms 가 걸린다면 틱이 최소 12.3 ms 였어야 한다.

**그런데 결론은 맞았다.** 이유가 대역폭이 아니라 이것이다.

> **USB CDC 는 PC 가 읽어가지 않으면 `Serial.printf` 가 그 자리에서 막힌다.**

호스트가 소비를 멈추면 TinyUSB 링버퍼가 차고, 쓰기가 타임아웃까지 블록한다.
그동안 IMU 읽기도 CAN 송신도 멈춘다. **분리해야 하는 이유는 대역폭이 아니라
호스트 의존성이다.** 그래서 4단계는 해야 하는 작업이 맞다.

`readStringUntil` 최대 1초 블록과 `lastLoop += 10000` 몰아치기 지적은 둘 다
맞았고, 각각 문자 단위 비동기 파서와 `vTaskDelayUntil` + 매 틱 재동기로 처리했다.

## 쓰는 법

3단계와 명령이 완전히 같다. `arm` `stop` `g` `ag` `ad` `kp` `kd` `f` `r` `d`
`dp` `dr` `zv` `zf` `zd` `zm` `?` `t` `z` 전부 그대로다.

```
① 24V 끄기
② zv_shaping_rtos 업로드   (도구 → USB CDC On Boot = Enabled)
③ 부팅 배너 확인
④ 24V 켜기                 ← 부팅 뒤에 켜면 모터가 disable 로 깨어난다
⑤ arm
```

부팅 배너에 `2단계 — 합력 벡터 목표각` 이라고 나온다. 3단계에서 안 고친 문구를
그대로 뒀다 (출력 동결). 아래 `zv1/zv0` 줄이 보이면 4단계다.

### 계측 줄

```
[rtos] 최대틱 556us  10ms초과 0  재동기 1 | TX실패 0 샘플드롭 0 이벤트드롭 0 명령드롭 0
```

2초마다 나온다. `#define RTOS_DIAG 0` 으로 두면 이 줄이 사라지고 출력이 3단계와
완전히 같아진다.

| 항목 | 정상값 | 의미 |
|---|---|---|
| `최대틱` | ~550 µs | 2초 창의 최대 제어 틱 시간. 예산 10,000 |
| `10ms초과` | 0 | 데드라인 놓친 횟수 |
| `재동기` | arm 당 1 | `arm` 의 `delay` 250 ms 뒤 시계 재설정 (설계대로) |
| `TX실패` | 0 | CAN 송신 실패. 모터 전원이 없으면 늘어난다 |
| `샘플드롭` | 0 | PC 가 안 읽어가면 늘어난다. **제어는 안 멈춘다** |

## 아직 안 된 것

### `ZV_FREQ` 실측 — 3단계에서 넘어온 숙제

`2.40Hz` 는 계산값이다. 물을 채우고 재야 한다.

```
한 번 기울였다 놓고 → 출렁임 10회에 몇 초인지 → 10 / 초 = Hz → zf<값>
```

### `t`(시험구동) 중에는 보호가 꺼져 있다 — 3단계에도 있는 문제

`motorSweep()` 은 앞에서 `motorsDisarm()` 을 부르므로 `armed == false` 다.
`drainCAN()` 안의 검사가 전부 `armed` 로 막혀 있어서, **8초 구동 내내
모터 이상·위치 폭주·피드백 두절이 감시되지 않는다.** 복귀 루프
(`while (fabsf(p) > 0.5f)`)는 `drainCAN()` 자체를 안 부른다.

이번에는 손대지 않았다 (제어 동작 동결). `sweeping` 플래그를 두고 검사 조건을
`(armed || sweeping)` 으로 바꾸면 된다. **실기에서 `t` 를 쓰기 전에 고치는 게 좋다.**

### 드라이버 `CAN Timeout = 0`

CAN 이 끊겨도 드라이버가 스스로 멈추지 않는다. 업로드 중 리셋되면 모터가
마지막 지령을 계속 붙잡는다. 로봇에 올리기 전에 200~500 ms 로 넣는 게 좋다.

### USB 로그 줄 깨짐 0.45%

1111줄 중 5줄에서 중간 몇 바이트가 빠졌다. 3단계 로그(1137줄)는 0줄이었으니
**이 구조에서 새로 생긴 것이 맞다.**

`Serial` 은 `io` 태스크 한 곳에서만 쓴다 (함수별 전수 감사 완료). 태스크 경합이
아니라 ESP32-S3 USB CDC 가 연속 `write()` 를 처리하다 흘리는 것으로 보이는데
**원인을 확정하지 못했다.**

지령은 CAN 으로 나가므로 **모터 제어와는 무관하고**, 로그 표시만의 문제다.
완화책은 `io` 태스크의 각 출력 뒤에 `Serial.flush()` 를 넣는 것이다 —
`io` 가 막혀도 제어는 코어 1 에서 계속 돈다. 아직 넣지 않았다.
